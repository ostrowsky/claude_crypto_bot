## 1. Инварианты (нарушение любого = остановка торговли и алерт)

1. **Ни одна позиция не живёт без защитного ордера на бирже дольше
   `TRADING_MAX_UNPROTECTED_SEC = 60`.** Бот уже падал молча (07-23 на 8 дней, 08-04, 09-28). В
   такой момент позиция без защиты ничем не ограничена.
2. **Биржа — источник истины.** Позиция существует, если на счёте есть остаток актива. Ордер
   существует, если биржа его возвращает.
3. **Каждый ордер идемпотентен:** `newClientOrderId = cb_<epoch8>_<sym>_<bar_ts>_<leg>`. Повтор
   после таймаута сначала ищет ордер по этому id.
4. **Все вызовы биржи асинхронные, с таймаутом**, в отдельной задаче asyncio с очередью. Event
   loop бота не ждёт биржу (урок 08-04).
5. **Решения принимает `trading_policy.py`** (общий с реплеем E1). Исполнитель решений не
   принимает, он только исполняет.

## 2. Связь с сигнальным ботом — только чтение (решение оператора 2026-10-10)

Трейдер — отдельный процесс из `trader/`. Код, конфиг и процесс бота он не меняет.

**Входы.** Трейдер читает хвост `files/bot_events.jsonl`, только чтение, с запоминанием смещения в
`trader/runtime/`. Источник сигналов — события `entry` (и `blocked` для политик, которые
отбирают из всех кандидатов) с признаками. `trading_policy.decide_entry()` решает, входить ли и
каким размером.

На первом шаге чемпион — «как вживую»: каждый вход бота, равные слоты. Это ровно то, что
посчитано в базовой линии (−0.83%/день): пока на демо генерируются данные исполнения, а не
прибыль. Задержка: бот пишет событие сразу при решении, трейдер опрашивает файл раз в 2–5 с.
Задержка сигнал → ордер измеряется и попадает в модель исполнения.

**Выходы** решает сам трейдер по своей политике (`trading_policy.exit_plan` бар за баром, на
барах из своей ленты WebSocket). Трейл считается **от цены фактического исполнения**. Событие
`exit` бота — не команда, а признак: политика «выходы как у бота» использует его как сигнал
выхода, остальные политики — свои правила. Бот о реальных позициях не знает; его виртуальные
позиции и кулдауны идут как прежде.

**Альтернатива** (если чтение лога бота окажется ненадёжным: ротация файла, задержки) —
собственный сигнальный контур трейдера. Это отдельная спека, она дороже: дублирует детекторы.

## 3. Машина состояний позиции (`trader/order_manager.py`)

```
SIGNAL -> ENTRY_SENT -> FILLED -(OCO <= 60 c)-> PROTECTED -> EXIT_SENT -> CLOSED
            |              |                        |
         REJECTED       PARTIAL -> защита на исполненное, остаток отменить
                                                    +-> TP_HIT / SL_HIT -> CLOSED (биржа закрыла сама)
```

| шаг | запрос | детали |
|---|---|---|
| вход | `POST /api/v3/order` MARKET BUY (`quoteOrderQty` = размер в USDT) или LIMIT IOC (вариант после H-проверки) | размер от `risk_manager`, округление по фильтрам; при отказе фильтра — запись, без повтора |
| защита | `POST /api/v3/orderList/oco` SELL на исполненное количество: верхняя нога `LIMIT_MAKER` (TP), нижняя `STOP_LOSS` (рыночный по срабатыванию; `TRADING_SL_ORDER_TYPE`) | `STOP_LOSS_LIMIT` может зависнуть при гэпе ниже лимита, поэтому по умолчанию рыночный стоп. Проверить на демо: допустимые `belowType` и `belowTrailingDelta` |
| отказ OCO | повтор ×3 (≤ 10 c) → только `STOP_LOSS` → рыночная продажа | инвариант 1 важнее TP |
| трейл | бот: при сдвиге стопа ≥ `TRADING_TRAIL_UPDATE_MIN_PCT = 0.2%` — отмена OCO (`DELETE /api/v3/orderList`) и новая OCO; окно без защиты < 1 c, не дольше лимита инварианта 1. Биржа: `belowTrailingDelta` (б.п. из ATR × k при входе), если демо его принимает | два ордера на продажу одного остатка спот не допускает, поэтому только OCO |
| выход по сигналу бота | отмена OCO → MARKET SELL всего свободного количества (округление по stepSize) | остаток ниже минимального лота = dust, учитывается в капитале |
| TP/SL сработали | поток пользователя (`executionReport` / `listStatus`) → CLOSED | бот отменяет виртуальную позицию в `monitor.py`, запускает кулдаун как после выхода |
| частичное исполнение | защита на исполненное количество, остаток входа отменить | |

**Уровни TP и SL** задаёт политика. Чемпион (как вживую): SL = начальный стоп трейла
(`max(k×ATR, floor×цена)`), TP = 0 (нет; верхняя нога OCO ставится далеко, на допустимом
`PERCENT_PRICE_BY_SIDE` пределе). Другие уровни — гипотеза H4 из E1, и включаются только после неё.

## 4. Риск-менеджер (`trader/risk_manager.py`)

Параметры — **решение оператора №3** (дорожная карта, раздел 5). Ниже предложенные значения; все
в `trader/trader_config.py`:

| параметр | предложение | действие |
|---|---|---|
| `TRADING_SIZING` | `"equal_slots"` (чемпион) / `"risk"` | равные слоты = 1/`MAX_OPEN_POSITIONS` капитала |
| `TRADING_RISK_PER_TRADE_PCT` | 0.5 | для `"risk"`: размер = 0.5% капитала / дистанция до SL |
| `TRADING_MAX_POSITION_PCT` | 10 | потолок одной позиции |
| `TRADING_CASH_RESERVE_PCT` | 10 | кэш, который не используется |
| `MAX_OPEN_POSITIONS`, кластер | 10, 2 (как сейчас) | |
| `TRADING_DAILY_LOSS_LIMIT_PCT` | 2 | R дня ≤ −2% → новых входов нет до 00:00 UTC; открытые позиции живут со своей защитой |
| `TRADING_KILL_SWITCH_DD_PCT` | 10 | просадка от максимума капитала ≥ 10% → `/flatten` и пауза до `/resume` оператора |
| `TRADING_LOSS_STREAK_PAUSE` | 5 убытков подряд → 4 ч без входов | |

На базовой линии sd дня 1.84%, поэтому дневной лимит −2% будет срабатывать часто. Это ожидаемо и
даёт данные для H6 (E1).

## 5. Сверка (`trader/reconcile.py`)

При старте и каждые `TRADING_RECONCILE_SEC = 300` сравниваются три источника: `account` +
`openOrders` + `openOrderLists` с биржи, позиции `order_manager`, журнал D.

| расхождение | действие |
|---|---|
| остаток актива без защитного ордера | поставить OCO по SL политики; если позиции нет в журнале — `STOP_LOSS` на −k×ATR от текущей цены и алерт |
| ордер без позиции | отменить, алерт |
| позиция в журнале, на бирже нет | восстановить закрытие по `myTrades`, CLOSED |
| капитал P против L (метрика) > 0.01% | `RECONCILE_FAIL`, новых входов нет до разбора |

## 6. Режимы и флаги

```python
TRADING_ENABLED: bool = False          # главный выключатель
TRADING_MODE: str = "paper"            # paper: fill_model на живых ценах; demo: ордера на demo-api
TRADING_MAX_UNPROTECTED_SEC: int = 60
TRADING_SL_ORDER_TYPE: str = "STOP_LOSS"
TRADING_TRAIL_UPDATE_MIN_PCT: float = 0.2
TRADING_RECONCILE_SEC: int = 300
# + параметры риска раздела 4
```

Paper использует тот же `order_manager` с исполнителем `fill_model.py` вместо биржи. Журнал тот
же, с полем `mode`. Порядок включения: paper 3–5 дней → demo.

**Откат:** `TRADING_ENABLED = False` (новые входы прекращаются, защита на бирже остаётся) + `/flatten`
(закрыть всё). Telegram-кнопка подтверждения обязательна для `/flatten`.

## 8. Отказы и что с ними делать

| отказ | поведение |
|---|---|
| бот упал с открытыми позициями | защита на бирже; при старте — сверка (раздел 5) |
| таймаут запроса ордера | `GET /api/v3/order?origClientOrderId=` перед повтором |
| техработы демо (ордера нельзя ставить и отменять) | новых входов нет; существующая защита стоит; после окончания — сверка |
| 418 (бан IP) | торговля остановлена, алерт; защита на бирже остаётся |
| −1021 (время) | пересинхронизация, повтор один раз |
| гэп сквозь стоп | рыночный `STOP_LOSS` исполняется по рынку; для `STOP_LOSS_LIMIT` — сторож: цена ниже лимита > 30 c и нога открыта → отмена и рыночная продажа |
| поток пользователя упал | опрос `openOrders` + `myTrades` раз в 60 c до переподключения |
