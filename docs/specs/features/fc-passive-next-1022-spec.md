## A. Теневая книга `FC_PASSIVE` на живом фандинге (`fc_shadow.py`)

### A.1 Что это

- Бумажная книга `FC_PASSIVE` на живых данных с **дня старта S**. S — первые полные сутки UTC после первого запуска: запуск 10:00 22-го → S = 23-е. S записывается в состояние и **больше не сдвигается**.
- Движок — **тот же `carry.simulate`** с `experiment_fc.passive_config()` и издержками уровня 1, на окне [S, сегодня). Отдельного движка нет, поэтому совпадение с проверкой обеспечено самой конструкцией.
- Капитал книги — 10 000 USDT. Доходности от масштаба не зависят, минимум сделки 10 USDT не срабатывает.
- Только бумага: без ключа, без ордеров, без подписанных запросов.

### A.2 Данные (публичные, только дозаписью, своё хранилище)

- `trader/runtime/fc_shadow/data/`:
  - `<SYM>_spot15m.npz` — `api.binance.com/api/v3/klines`;
  - `<SYM>_perp15m.npz` — `fapi.binance.com/fapi/v1/klines`;
  - `<SYM>_funding.npz` — `fapi.binance.com/fapi/v1/fundingRate` с `startTime`.

  Для BTCUSDT и ETHUSDT.
- Начало хранилища — за 35 дней до S (запас для проверок данных).
- Исследовательские хранилища `runtime/history`, `runtime/perp_history`, `runtime/funding` книга не пишет.

### A.3 Шаг

- `fc_shadow.py step` добавляется в `run_shadow.cmd` после шага E7, со своей проверкой `errorlevel`. Сбой шага FC не мешает E7.
- Шаг **идемпотентен**:
  - повторный запуск на тех же данных не меняет состояние и не дублирует строки журнала;
  - после сна машины он догоняет пропущенные дни.
- Каждый шаг заново считает `carry.simulate` на [S, сегодня). Поэтому повтор и догон дают тот же результат по построению.
- Шаг пишет в `trader/runtime/fc_shadow/`:
  - `state.json` — S, время последнего шага, отметки капитала, ряд R, число сделок, ликвидаций и маржинальных стопов, фандинг, найденные аномалии;
  - `ledger.jsonl` — закрытые сделки и найденные проблемы данных, каждая запись один раз.
- Закрытие на краю окна (`reason = "flush"` в `simulate`) — не сделка, а способ посчитать итог. В журнал и в число сделок оно не попадает. Иначе каждый шаг писал бы ложную сделку.
- Интерфейс, который фиксируют тесты:
  - `step(now, fetch, state_path, ledger_path, enabled)`;
  - `fetch(...)` возвращает `{sym: {"spot", "perp", "funding"}}`. Настоящий `fetch` дописывает хранилище §A.2, в тестах он подменяется;
  - `market_from(data)` строит `carry.Market`;
  - `data_checks(data, day_from, day_to)` и `book_checks(state)` возвращают список проблем `{"kind", ...}`;
  - `readout(state)` — чистая функция; файл `READOUT_FC.json` пишет только команда `readout`.
- Флаг `trader_config.FC_SHADOW_ENABLED = True`. При False шаг ничего не делает. Откат — False.

### A.4 Проверки данных → `ANOMALY` (раньше срока)

- В 15m-барах любой ноги дыра больше 1 часа внутри окна [S, сегодня). Дыры до S — не аномалия этой книги.
- Пауза между событиями фандинга больше 12 часов (интервал BTC/ETH — 8 ч, плюс 4 ч запаса).
- Отношение close фьючерса к close спота за сутки вне ±5%.
- Ликвидация в книге. Маржинальный стоп — штатная механика, не аномалия, но он пишется в журнал.

### A.5 Разбор `FC-SHADOW` (зафиксирован до запуска, `READOUT_FC.json`, считает `fc_shadow.py readout`)

| статус | условие |
|---|---|
| `COLLECTING` | меньше 90 полных дней с S |
| `KEEP` | ≥ 90 дней, нижняя граница 95% средней дневной R > 0, 0 ликвидаций |
| `REJECT` | ≥ 90 дней и (верхняя граница 95% < 0 или хотя бы одна ликвидация) |
| `INCONCLUSIVE` | ≥ 90 дней, иначе; окно продлевается, критерии не ослабляются |
| `ANOMALY` | любая проверка §A.4, в любой день |

- Почему 90 дней: при sd ≈ 0.0105 %/день (проверка 2026 года) и средней ≈ 0.0024 нижняя граница выходит выше нуля примерно через 75 дней, если средняя сохранится. Срок — S + 90 дней (при S = 2026-10-23 это не раньше 2027-01-21).
- `KEEP` даёт право на отдельную спеку исполнения на демо после `GO` F0. `REJECT` останавливает линию FC.

## B. Скрипт F0 (`_smoke_demo_futures.py`, логика в `demo_futures.run_f0`)

### B.1 Безопасность

- **Без `--go` скрипт печатает план и не делает ни одного запроса.**
- Подписанные запросы — только на `demo-fapi.binance.com` (`exchange_client.ALLOWED_HOSTS`, только `demo-*`).
- **Позиции не открываются.** Ордер — только `POST /fapi/v1/order/test`, биржа его проверяет, но не исполняет. `POST /fapi/v1/order` в F0 запрещён (тест).
- С `--go` оператор разрешает три **изменения настроек** демо-счёта для BTCUSDT и ETHUSDT:
  - режим позиций one-way — только если сейчас hedge;
  - маржа ISOLATED;
  - плечо 1.

  Код −4046 («менять не нужно») считается успехом.
- Ключи не печатаются; все запросы идут в журнал аудита, как у клиента спота.

### B.2 Что проверяет (пункты §10 родительской спеки)

| пункт | запрос | результат |
|---|---|---|
| 3 | `GET /fapi/v1/time` (публично) | связь с демо |
| 1–2 | `GET /fapi/v2/account` | `account_ok`, `futures_permission`. Отказ по ключу (HTTP 401 или коды −2014, −2015, −2008) → `futures_permission = False`, дальше подписанных запросов нет, итог `NO_GO` |
| 4 | `GET /fapi/v2/balance` | `futures_balance_usdt` |
| 5 | `GET` / `POST /fapi/v1/positionSide/dual` | `one_way_mode` |
| 6 | `POST /fapi/v1/marginType`, `POST /fapi/v1/leverage` | `isolated_ok`, `leverage1_ok` |
| 7 | `GET /fapi/v1/commissionRate` (BTCUSDT) | `commission` = taker, maker |
| 8 | `POST /fapi/v1/order/test` (MARKET SELL BTCUSDT, наименьшее допустимое количество — см. ниже) | `order_test_ok` |
| 9 | спотовый и фьючерсный `exchangeInfo` | `lot_match_ok` |
| 10 | `GET /fapi/v1/income?incomeType=FUNDING_FEE` | `funding_income_seen` (True, если есть строки; иначе None) |
| 11 | `premiumIndex` на `demo-fapi` и `fapi` (BTC, ETH) | `demo_vs_live_funding_gap_bp` = max \|demo − live\| × 10 000 |

- **`lot_match_ok`** проверяется на **номинале будущей книги**, `LOT_NOTIONAL_USDT = 2500`: 10 000 USDT / 2 пары / (1 + 1/L) при L = 1. По цене маркировки фьючерса:
  - количество спота округляется вниз к шагу спота (`LOT_SIZE`);
  - количество фьючерса — к шагу фьючерса (`MARKET_LOT_SIZE`, если есть, иначе `LOT_SIZE`);
  - разница количеств ≤ одного шага фьючерса;
  - оба количества ≥ минимального;
  - номинал каждой ноги (количество × цена) ≥ её минимума (`MIN_NOTIONAL` у фьючерса, `NOTIONAL` / `MIN_NOTIONAL` у спота).
- **Почему не 100 USDT.** На 100 USDT BTC не собрать: шаг фьючерса 0.001 BTC при цене около 84 000 — это 84 USDT, ниже минимума фьючерса 100 USDT (тест). 100 USDT на фьючерсном кошельке — только условие «кошелёк пополнен».
- **Количество для тестового ордера** — `order_test_qty(perp_info, mark)`: наименьшее кратное шагу, не меньше минимального количества, с номиналом ≥ минимума × 1.05. Пример: BTC при 84 000 → 0.002, ETH при 2 500 → 0.009.
- Итог — `demo_futures.readiness(results)` (`GO` / `NO_GO`, список недостающего, предупреждения). Пишется в `trader/runtime/futures/F0_<UTC>.json` (`demo_futures.F0_DIR`).
- Интерфейс: `run_f0(go, fut=None, spot=None, out_dir=None)`:
  - `fut` — клиент на `demo-fapi`; он же берёт живой `premiumIndex` с `fapi` без подписи;
  - `spot` — клиент демо-спота (для `exchangeInfo`).
- Новые методы клиента: `fut_time`, `fut_account`, `fut_balance`, `fut_position_side`, `fut_set_position_side`, `fut_margin_type`, `fut_leverage`, `fut_commission`, `fut_test_order`, `fut_income`. Метода для настоящего фьючерсного ордера нет (тест).
- **Время для подписи на фьючерсном адресе.** Клиент сейчас синхронизирует время по `/api/v3/time` — такого пути на `fapi` нет. Для адреса `*fapi*` путь меняется на `/fapi/v1/time` (тест).

## C. Исправление: интервал вердикта на уровне 1 − α

- **Дефект** (журнал FC, 10-22): `experiment_fc.verdict` берёт `lo95` из `simulate`, где `aggregate` считается на α = 0.05 при любом k. При двух открытых гипотезах (α = 0.025) `profitable` оценивался бы по слишком узкому интервалу.
- **Исправление:** новая функция `experiment_fc.judge(kind, e, alpha)` считает интервал средней R заново — `daily_revenue.aggregate(e["_series"], alpha=alpha)` — и передаёт его в `verdict`. В вердикт пишутся `alpha` и границы `lo` / `hi`. `run_test` вызывает только `judge`, `verdict` напрямую в нём не остаётся.
- На уже открытую проверку `FC_PASSIVE` (k = 1, α = 0.05) это не влияет. Тест сравнивает `judge` с `aggregate` на обоих уровнях.
- **Аудит соседей.** XSMOM и S1 считают парную разницу с `alpha` правильно. S1 открывает одну гипотезу, поэтому α = 0.05 там верно. Других мест с этим дефектом не найдено.
