## 0. Решение оператора и что из него следует

**Решение №2 (2026-10-14):** «использовать для Binance трейдера все монеты, доступные на спотовом рынке для торговли».
Правило §14 CLAUDE.md остаётся в силе для вотчлиста сигнального бота (93 монеты) и на трейдер не распространяется.

Сигнальный бот оценивает только свои 93 монеты, а трейдер берёт входы из его событий. Чтобы торговать остальные
пары, трейдеру нужен **свой генератор входов** на всём универсуме. Бот при этом не меняется: его код импортируется
только на чтение, как уже сделано с `indicators` и `exit_validator`.

Торговый универсум (`trading_universe.py`, exchangeInfo демо от 2026-10-10):
- 494 пары к USDT со статусом TRADING и разрешённым спотом;
- исключены 254 пары не в статусе TRADING и 12 пар стейблкоинов и фиата (на них нет движений, которые ищет стратегия);
- у 105 пар есть история бота, у 389 — нет.

## 2. B1 — история свечей (CPU, публичный API)

- **Пары.** Универсум TRADING (494) **плюс делистнутые пары (BREAK), у которых есть свечи**. Без делистнутых
  проверка в прошлом оптимистична: мёртвые монеты выпали бы из выборки (ошибка выжившего, TH-05). Пара участвует
  в реплее только в те дни, когда торговалась (есть свечи). Проверено 2026-10-14: живой API отдаёт свечи по делистнутым парам до даты делистинга
  (BCCUSDT, EOSUSDT, ICXUSDT, VENUSDT, NULSUSDT, PAXUSDT); в exchangeInfo демо таких пар к USDT — 254.
- **Период:** с 2023-01-01 или с даты листинга, если она позже, до последнего закрытого бара. Граница 2023-01-01 —
  компромисс между объёмом выгрузки и хранения и длиной истории; раскрывается.
- **Источник** — `GET /api/v3/klines` живого рынка `api.binance.com` (тот же, что у бота), только 15m. 1h строится
  агрегацией 15m: OHLCV 1h = агрегация четырёх 15m — открытие первой, максимум, минимум, закрытие последней,
  сумма объёма. Равенство с API 1h проверяется тестом на выборке пар.
- **Хранение:** `trader/runtime/history/<SYM>_15m.npz` (t, o, h, l, c, v; float64 для цен). Дозапись новых баров;
  проверка непрерывности: пропуски > 1 бара записываются в журнал пары, не заполняются.
- **Темп** ≤ 5 запросов в секунду, общий счётчик веса. IP общий с ботом и вторым ботом на машине, поэтому
  выгрузка идёт в фоне с перерывами, а не одним рывком.

## 3. B2 — генератор входов (CPU)

Для каждой пары и таймфрейма (15m, 1h), на каждом закрытом баре i:
1. `feat = indicators.compute_features(o, h, l, c, v)` — функция бота, импорт только на чтение;
2. условия бота: `check_entry_conditions(feat, i, c, tf)`, `check_breakout_conditions`, `check_retest_conditions`,
   `check_impulse_conditions`, `check_alignment_conditions(feat, i, tf)` и `get_entry_mode(feat, i)` — как в
   `monitor.py` (~L4072);
3. сработавшее условие → событие-кандидат `{sym, tf, ts = закрытие бара, price = c[i], mode, trail_k}` в формате
   событий бота. Тогда реплей E1 и исполнитель читают его без изменений.

**Чего генератор не повторяет** (раскрывается):
- ML-гейт, ранкер, бандит, guard'ы, ротацию и кулдауны бота: они живут внутри `monitor.py` и обучены на вотчлисте;
- порядок обхода монет.

Поэтому генератор даёт **надмножество** входов бота. Отбор — политика трейдера (слоты, лимит в день), а не гейты бота.

**Сверка с ботом (обязательна до денег):** на 93 монетах вотчлиста за 03-03..10-13 считаются:
- доля реальных входов бота (`bot_events` `entry`), у которых генератор даёт кандидата того же символа и
  таймфрейма в пределах ±1 бара — полнота генератора относительно бота;
- доля кандидатов генератора, которые бот взял, — насколько генератор шире.

Полнота < 0.79 (до 2026-10-14 — 0.80, см. §8) → генератор не воспроизводит правила бота: остановка, разбор расхождений, денежная проверка не
запускается.

## 4. B3 — проверка в деньгах (E1, протокол L3)

- **Политика:** X4 (выходы P-1 с полом 8%, 96 баров), 10 равных слотов, издержки taker + 8 б.п. на сторону.
  Допуск входа: кандидаты генератора в порядке времени; одна позиция на монету; кулдаун после выхода = кулдаун
  бота (`COOLDOWN_BARS`).
- **Руки (одинаковая политика, разный набор монет):**
  - `W93` — генератор на вотчлисте;
  - `WALL` — генератор на всём универсуме (вотчлист + новые + делистнутые в дни торговли);
  - `WNEW` — только новые монеты;
  - справочно `BOT` — реальные входы бота с X4 (= E7/H3), только на периоде 03-03..10-13.
- **Деление по времени** (зафиксировано до прогона): train 2023-01-01..2025-12-31, test 2026-01-01..последний
  полный день. Test открывается **один раз**.
- **Критерии на test:**
  - `improves`: парная разница дневной выручки WALL − W93, нижняя граница 95% ДИ > 0 (блочный бутстрэп по 5 дней);
  - `profitable`: выручка WALL, нижняя граница > 0;
  - контроль «торговать меньше / иначе»: WALL против 20 случайных прореживаний W∪новых до того же числа сделок —
    WALL должен быть лучше медианы случайных; иначе эффект объясняется числом сделок, а не выбором монет.
- **Срезы** (справочно): по месяцам; по обороту пары (квартили 24-часового оборота в момент входа) — тонкие пары
  дают нереалистичные исполнения; по возрасту листинга.
- Исполнение в реплее идёт по ценам живого рынка, исполнение на демо — по демо-стакану. Расхождение mid демо и
  живого рынка измеряет запись A0. Для новых пар оно добавляется в отчёт по мере накопления, не в критерий.

### 4a. Сетка баров для реплея (уточнено 2026-10-14 при коде)

Плотная матрица сетки E1 на ~700 пар × ~130 тыс. 15-минутных баров с 2023 года — это ~1.4 ГБ даже в float32.
На машине свободно ~1.7 ГБ, и её делят два бота. Поэтому для B3 используется **ленивая сетка** `trader/lazy_grid.py`:
- каждая пара хранится на диске отдельным плотным массивом от первого до последнего бара (C — float64; O, H, L, V,
  ATR — float32);
- пропуск бара = NaN, как в сетке бота; ATR считается функцией бота `indicators._atr` по барам пары без пропусков
  и раскладывается по своим местам, так же, как `execution_replay._grid` достраивает L и V;
- чтение через `np.load(mmap_mode="r")`, в память попадают только запрошенные бары.

Интерфейс тот же, что читает `execution_replay.run` и `trading_policy.exit_plan`:
`syms`, `col`, `t0`, `N`, `idx(dt)`, `C/O/H/L/V/ATR[ix, j]`; вне диапазона пары — NaN.

**Требование:** на одних барах и кандидатах `execution_replay.run` с ленивой сеткой и с плотной даёт одинаковые сделки,
дневной ряд и итоговый капитал.

### 4b. Запуск B3 (уточнено 2026-10-14, до любых данных B3)

1. **Кандидаты.** Генератор по каждой паре на всей её истории с 2023-01-01: 15m и 1h из 15m.
   - Кэш по паре: `trader/runtime/experiments/b3_cands/<SYM>.jsonl` + `<SYM>.meta.json` (sha кода `candidate_gen.py` и
     конфига бота). При несовпадении sha кэш пересчитывается.
   - Считается параллельно (по умолчанию 3 процесса), с продолжением после обрыва.
2. **Сетка** — `lazy_grid.build_all()` по всем парам с историей; t0 = 2023-01-01 00:00 UTC.
3. **Политика B3** — X4 (выходы P-1, пол 8%, 96 баров), 10 равных слотов, одна позиция на монету
   (`one_per_symbol=True`), кулдаун после выхода = `COOLDOWN_BARS` бота. Издержки — taker + 8 б.п. на сторону
   (`fill_model` уровень 1). Кандидаты допускаются в порядке времени.
4. **Train** (`B3_TRAIN.json`): W93, WALL, WNEW на 2023-01-01..2025-12-31 — R %/день с ДИ, сделки, разложение.
   Test-кандидаты на этом шаге не читаются.
5. **Test** (`B3_TEST.json`), ровно один раз: файл-метка `B3_TEST_OPENED.json` и запись в журнал попыток; без
   `B3_TRAIN.json` не запускается. Руки на 2026-01-01..последний полный день; парная разница WALL − W93 (`daily_revenue.paired`).
6. **Случайный контроль** (уточнение формулировки §4):
   - 20 случайных подвыборок пула кандидатов WALL, каждая того же размера, что пул W93 (зёрна 0..19);
   - `beats_random` = средняя R у WALL > медианы R подвыборок.

   Вопрос контроля: даёт ли выигрыш ширина пула (больше кандидатов, лучше выбор при тех же слотах) или его дал бы
   любой набор монет того же размера. Справочно печатается и W93 против той же медианы: особый ли вотчлист.

7. **Память кандидатов.** Генератор даёт порядка 2 млн кандидатов (замер на AAVEUSDT: ~1 600 на 40 тыс. баров).
   Обычными словарями это 1.5–3 ГБ при свободных ~1.7 ГБ. Поэтому кандидат — компактный объект `Cand` (`__slots__`,
   интерфейс Mapping): `execution_replay.run` и `attach_grid` читают и пишут его как словарь, а `dict(c)` работает.
   Требование: `run()` с `Cand` и со словарями даёт одинаковый результат.

## 5. B4 — живые данные и тень (после B3, только при `improves`)

- Поток `kline_15m` по WebSocket всего универсума: комбинированные потоки, ≤ 1024 на соединение; 1h — агрегацией.
- На закрытии бара — генератор (§3) → события в `trader/runtime/signals/events.jsonl` (только дозапись).
- Источник входов исполнителя и теневых книг — флаг `TRADER_SIGNAL_SOURCE`: `"bot"` (сейчас) | `"wide"` | `"both"`.
  Переключение — только после теневой книги на широком универсуме.
- **Гейт B:**
  - все пары оценены на каждом закрытии бара с задержкой ≤ 60 с;
  - 0 переполнений очереди за 48 ч;
  - разрыв «реплей ↔ тень» по сделкам в пределах модели исполнения.

## 6. Требования к коду (тесты до кода)

1. **История:**
   - сборка 1h из 15m совпадает с API 1h (синтетика + выборка);
   - дозапись без дублей;
   - пропуски записываются, не заполняются;
   - делистнутые пары включаются только в дни со свечами.
2. **Генератор:**
   - на синтетических барах, где условие бота срабатывает, — событие в формате бота с ts закрытия бара и price = c[i];
   - функции бота вызываются, а не копируются (проверка по источнику);
   - только закрытые бары.
3. **Сверка:** полнота и ширина считаются по ±1 бару одного таймфрейма; при полноте < 0.79 денежная проверка не
   запускается.
4. **Ленивая сетка:** паритет `run()` с плотной сеткой; пропуск — NaN; вне диапазона — NaN; ATR = функция бота.
5. **Запуск B3:** кандидаты переводятся в формат реплея (kind entry, ts — datetime); политика B3 = §4b.3; кэш
   кандидатов переиспользуется при совпадении sha и пересчитывается при расхождении; train не видит test;
   test без train не запускается и открывается один раз; сквозной прогон на синтетике даёт все поля вердикта и
   20 воспроизводимых случайных R.
6. **Деньги:**
   - руки W93 / WALL / WNEW на одних данных и одной политике;
   - test открывается один раз (журнал попыток, `money_validator.log_trial`);
   - критерии §4 включительно;
   - контроль случайного прореживания воспроизводим по зерну.
7. **Границы:**
   - запись только в `trader/runtime/`;
   - `files/`, `history/` и `config.py` бота только читаются;
   - запросы без подписи и только на `api.binance.com`;
   - нет Telegram.
