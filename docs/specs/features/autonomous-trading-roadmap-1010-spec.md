## 0. С чего начинаем — честная базовая линия

Вопрос: если торговать ровно тем, что бот выдаёт сегодня, сколько он принесёт в день?

Данные: каждая реальная пара вход→выход бота в `bot_events.jsonl` с 2026-03-01. Это 5 753 сделки
за 200 дней (03-03..10-10), выходы собственные, pnl берётся из события выхода. Позиция = 1/10
капитала, максимум 10 одновременно (11-я пропускается, взято 5 651). День считается по UTC-дате
выхода, только реализованный результат.

| | значение |
|---|---|
| сделок в день | 28.3, медианное удержание 2.0 ч (p90 7 ч) |
| результат сделки **до** комиссий | среднее **−0.093%**, медиана −0.31%, прибыльных 40% |
| доля сделок, покрывающих комиссию 0.20% | 35.8% |
| день, комиссия taker 0.10%+0.10% | **−0.83% капитала в среднем**, sd 1.84%, t = −6.4 |
| прибыльных дней | 28% |
| капитал 1.00 через 200 дней (сложный процент) | **0.165** |
| месяцы | все 8 отрицательные (−6.6..−28.4%) |
| с комиссией BNB 0.075%×2 | −0.69%/день; по отчётной 0.10% round-trip — −0.54%/день |
| только комиссии | 28.3 × 0.20% / 10 = **−0.57%/день** |

Ни один режим не прибылен даже до комиссий: impulse_speed/15m −0.018% (n=1609),
alignment/15m −0.065%, trend/15m −0.159%, impulse/15m −0.294%.

**Выводы для плана:**
1. Если автоматизировать нынешние решения, деньги будут теряться каждый день. Подключение к бирже
   выручку не создаст. Блокер цели — **отсутствие положительного ожидания у сигналов**, а не
   инфраструктура. Модели обучались на «ранний захват движения» и «пик ≥ 2% за 5 баров», а не на
   деньги. По `model-health-1005-spec.md` IC `ml_proba` с доходностью через 2.5 ч равна **−0.14**:
   фильтр выбирает всплески, которые откатываются.
2. Дневная выручка слишком шумна, чтобы учиться по ней напрямую. При sd 1.84%/день, чтобы отличить
   +0.10%/день от нуля (мощность 80%), нужно **≈ 2 650 дней**. Контур учится на чистом ожидании
   каждой сделки (тысячи сделок) и на **парных** сравнениях политик в одни и те же дни: реплей и
   теневые портфели. Дневная выручка остаётся итоговой метрикой и судит только длинные окна.
3. Деньги в «кэше» дают 0, и это лучше −0.83. Политика «не торговать» — законный чемпион, пока
   ничто не обгоняет ноль.
4. Оговорки к базе: нет проскальзывания и спреда (реально будет хуже); открытые позиции не
   переоцениваются; ротация и кулдауны как в живом боте.

## 1. Метрика — DailyRevenue v1 (ObjectiveContract v2)

```
mission_kpi    R_d = (E_end − E_start − net_transfers) / E_start, UTC-сутки, E = весь капитал
               демо-счёта в USDT по mid-цене (все активы, включая открытые позиции);
               комиссии и проскальзывание входят автоматически
aggregate      среднее R за 30 дней с 95% ДИ + сложный 30д результат + макс. просадка;
               ДИ включает 0 -> «рано судить» (TH-10)
benchmarks     в той же строке: USDT (0), BTC buy&hold, равновзвешенный универсум
decomposition  сделки/день × (доля прибыльных × средний выигрыш − доля убыточных × средний
               проигрыш) − комиссии − проскальзывание; экспозиция (средняя доля в позициях);
               по режиму / причине выхода / режиму рынка
learning KPI   чистое ожидание сделки (после комиссий и проскальзывания) с ДИ; парная разница
               дневной выручки кандидата и чемпиона в теневых портфелях
guardrails     макс. просадка, худший день, доля дней с нарушением дневного лимита убытка,
               незащищённые позиции = 0, расхождение учёта и биржи = 0
incomplete     дни простоя, частичные дни, дни сброса демо-баланса -> UNKNOWN, не успех и не провал (TH-05)
diagnostic     NS_EarlyCapture_top20_v2 продолжает публиковаться
```

## 2. Принципы, которые не меняются

- **Только демо.** Хост `demo-api.binance.com` зашит в коде. Mainnet отвергается кодом, а не
  флагом. Переход на реальные деньги — отдельное решение оператора и отдельная спека, в этот план
  не входит. Binance прямо пишет, что демо-данные «реалистичные, но не реальные» и стратегия,
  работающая на демо, может не работать вживую.
- **Ключи создаёт оператор**, хранятся в `files\.env` (в `.gitignore`). Права ключа: только Spot
  trading, белый список IP. Claude ключи не видит и не вводит.
- **Каждое изменение поведения — за флагом, сначала shadow/paper**, затем демо, с заранее
  записанным readout (`files/readout_registry.json`) и откатом (TH-07).
- **Одна функция решения для реплея и для живой торговли.** Расхождение «обучение ↔ живая
  торговля» — главный диагностический сигнал (§0 правило 3). Оно возникает, если у бэктеста свой
  код.
- **Только дозапись** (append-only) в журналы сделок. Урок 2026-08-04: полная перезапись больших
  файлов замораживала event loop.
- **Биржа — источник истины** о позициях и ордерах. Бот сверяется с ней при старте и периодически.
- Проверка гипотез — на максимальном периоде, с делением по времени. Отрицательные результаты
  коммитятся, `already_tried.jsonl` обязателен.

## 3. Этапы

Этапы A–D (инфраструктура) идут параллельно с этапом E (поиск преимущества): демо-деньги
ненастоящие, а реальные исполнения — данные, которых сейчас нет (проскальзывание, задержки,
отказы). Выручка начнёт расти только после E.

### Этап A — подключение к демо-счёту (задачи 1, 2)

| Что | Детали |
|---|---|
| Ключ | Оператор: demo.binance.com → Binance Demo Trading → API Management. Только Spot trading, IP whitelist → `files\.env` (`BINANCE_DEMO_API_KEY`, `BINANCE_DEMO_API_SECRET`) |
| `trader/exchange_client.py` | Подписанный REST к `https://demo-api.binance.com/api`; синхронизация serverTime + recvWindow; учёт веса (`X-MBX-USED-WEIGHT-*`) и бэкофф; идемпотентный `newClientOrderId`; кэш `exchangeInfo` с фильтрами (LOT_SIZE, PRICE_FILTER, NOTIONAL, MAX_NUM_ORDERS); `GET /api/v3/account` (балансы), `/api/v3/account/commission` (реальные ставки); `POST /api/v3/order/test` (сухой прогон); поток пользователя (исполнения) через WS API `wss://demo-ws-api.binance.com/ws-api/v3` |
| `trader/trading_universe.py` | Все пары `status=TRADING`, quote USDT, spot разрешён, OCO разрешён. **Фильтр ликвидности:** 24ч оборот ≥ X, спред на демо-стакане ≤ Y б.п., расхождение mid демо и живого рынка ≤ Z б.п. Обновление раз в сутки → `trader/runtime/trading/universe.json` |
| Баланс | Свободный USDT и активы → equity snapshot при старте и каждые 5 минут |
| Флаги | `TRADING_ENABLED = False`, `TRADING_MODE = "paper"` (`"demo"` после этапа C) |

**Конфликт с §14 CLAUDE.md** («watchlist IMMUTABLE — DO NOT EXPAND»). Это правило оператора, и
его снимает только оператор. Запрос «все монеты, доступные на демо» — явная его ревизия для
демо-торговли. Предлагаю отдельный торговый универсум с фильтром ликвидности. Нынешние 93 монеты
остаются как сигнальный watchlist до решения об их слиянии. Без фильтра неликвидные пары дадут
нереалистичные исполнения на тонком демо-стакане.

**Гейт A:**
- баланс и `exchangeInfo` читаются;
- `order/test` проходит фильтры на 20 случайных парах;
- универсум собран, расхождение демо/живого рынка измерено по каждой паре;
- `test_exchange_client.py` проходит;
- ни одного реального ордера.

### Этап B — данные под весь универсум (задача 3)

- **WebSocket вместо опроса.** Сейчас `MAX_POLL_PER_CYCLE = 45` монет за 60 с. Для ~93 монет это
  ~3 минуты на полный проход, для нескольких сотен — около 10 минут и больше. Нужны
  комбинированные потоки kline 15m/1h + bookTicker (в `ws_manager.py` уже есть комбинированные
  потоки, до 1024 на соединение) и оценка на закрытии бара.
- **История для новых пар**: бэкфилл 15m/1h за максимальный период (`_backfill_klines_history.py`).
  Без неё нет индикаторов и обучения.
- **Откуда брать цены** — решается по замеру этапа A. Признаки и обучение — на живых данных
  (вся история бота оттуда). Цены исполнения, TP/SL и учёт — на демо. Если расхождение мало,
  используем одну ленту.
- **Данные для денежных решений:** спред и глубина первых уровней (оценка проскальзывания под
  размер позиции), реальные ставки комиссий, позиционирование деривативов (уже пишется
  `positioning_recorder.py`).
- Никаких синхронных записей больших файлов в event loop.

**Гейт B:**
- все пары универсума оцениваются на каждом закрытии бара с задержкой ≤ 60 с;
- 0 предупреждений о лаге loop за 48 ч;
- отчёт о расхождении цен демо и живого рынка готов.

### Этап C — исполнение: покупка, TP/SL, продажа (задачи 4, 5)

| Модуль | Роль |
|---|---|
| `trader/risk_manager.py` | Размер = риск r% капитала / дистанция до SL (волатильностный таргетинг), потолок 10% на позицию, ≤ `MAX_OPEN_POSITIONS`, ≤ 2 на кластер корреляции (уже есть), резерв кэша; **дневной лимит убытка** (например −2% → новых входов нет до следующих UTC-суток); **аварийный стоп по просадке**; пауза после серии убытков |
| `trader/order_manager.py` | Машина состояний позиции: `PENDING → FILLED → PROTECTED → EXITING → CLOSED`. Вход MARKET или LIMIT IOC. Сразу после исполнения — **OCO на продажу** (TP limit + SL stop-limit, `POST /api/v3/orderList/oco`) либо всё одним `orderList/otoco`, проверить на демо первым тестом. Выходы бота (трейл ATR, режим лидера, выходы по слабости) — через `order/cancelReplace` защитного SL или отмена OCO + MARKET sell. Остатки (dust) учитываются |
| `trader/execution_sim.py` | Бумажные исполнения с тем же интерфейсом: комиссии, спред, проскальзывание по глубине. Используется в paper-режиме и в реплее этапа E |
| Сверка | При старте и каждые N минут: позиции, ордера, балансы бота против биржи; осиротевшие ордера и позиции → алерт и защита |
| Telegram | `/status`, `/pause`, `/resume`, `/flatten` (закрыть всё), уведомления о входе/выходе/TP/SL |

**Почему защита стоит на бирже, а не только в боте:** бот уже умирал молча — 07-23 на 8 дней,
08-04, 09-28. Любая позиция без защитного ордера на бирже в такой момент ничем не ограничена.
Правило: незащищённая позиция живёт ≤ 60 с.

Порядок: paper 3–5 дней на живых данных → демо 7 дней. Откат: `TRADING_ENABLED = False` +
`/flatten`.

**Гейт C (7 дней демо):**
- 0 позиций без защиты дольше 60 с;
- 0 расхождений сверки;
- 0 отказов по фильтрам;
- проскальзывание и задержка исполнения измерены (paper против демо по каждой сделке).

Дневная выручка на этом этапе будет **отрицательной** — это база, а не провал (раздел 0).

### Этап D — учёт и подача в контур обучения (задача 6)

- `trader/trade_ledger.py` → `trader/runtime/trading/ledger.jsonl` (только дозапись): каждое решение
  (вход/пропуск с причиной и снимком признаков), ордер, исполнение, комиссия, срабатывание
  TP/SL, отмена, сверка. Отдельно `equity_snapshots.jsonl` (каждые 5 мин и закрытие UTC-суток).
- `trader/daily_revenue.py`: метрика раздела 1 с бенчмарками, покрытием и днями простоя → в
  `metrics_daily.jsonl` и блок «Выручка» в утреннем отчёте.
- **Разрыв реплей ↔ факт по дням:** выручка, которую реплей предсказал для фактических решений
  дня, против реализованной. Это проскальзывание, задержка и логика исполнения в одной цифре.
  Публикуется рядом, не сворачивается в одно число (§0 правило 3).
- Метки обучения: реализованный чистый результат каждого решения (после комиссий и
  проскальзывания) дописывается к датасетам дозаписью.

**Гейт D:**
- учёт сходится с балансом биржи до цента каждый день;
- метрика воспроизводится скриптом с нуля;
- `truth_harness.py` знает новую метрику (машинно проверяемые утверждения, TH-09).

### Этап E — поиск положительного ожидания (ядро задачи 7; это и есть блокер)

| Шаг | Суть | Почему |
|---|---|---|
| E1. Реплей с исполнением | Движок `exit_validator` (все реальные сделки с 03-01) + комиссии + проскальзывание из этапа C + размер позиции + слоты. Та же функция решения, что вживую | Без этого любая гипотеза оценивается без денег |
| E2. Цель модели = деньги | Метка — чистый результат сделки после комиссий при текущей политике выхода, а не «пик ≥ 2% за 5 баров». Вход только при прогнозе чистого ожидания > 0 (калиброванный). Ворота промоушена ML судят по ожиданию допущенных сделок, а не по AUC | Нынешняя цель выбирает откатывающиеся всплески (IC −0.14) |
| E3. Меньше сделок | 28 сделок/день съедают 0.57%/день одной комиссией. Цель оператора от 09-27 — «1–3 лидера в день» | Комиссия больше среднего результата сделки до комиссий |
| E4. Выходы в деньгах | Правило «держать после дивергенции RSI при прибыли ≥ +0.5%» (принято офлайн 10-05), режим лидера X-9c (вердикт 10-12), широкий трейл на ракетах | Захват движения — слабый множитель (0.22–0.26) |
| E5. Режим рынка | Не открывать новые позиции в дни слабой ширины рынка; спот не умеет шортить, кэш = 0 | Все 8 месяцев отрицательны; в плохие дни лучше не торговать |
| E6. Размер позиции | По волатильности и прогнозу ожидания; потолки риска | Тот же сигнал с другим размером — другая выручка |
| E7. Теневые портфели | N политик-кандидатов торгуют на бумаге на живых данных параллельно с чемпионом на демо, с независимым состоянием (shadow twin, §6.2 целевой спеки). Сравнение — парная разница дневной выручки | Единственный способ сравнивать политики быстрее, чем за годы |
| E8. Позиционирование | Тест 2026-10-18 (данные деривативов на пересечении +2.5%) — последний непроверенный источник раннего входа | Цена/объём/поток раннего входа не дают (10 гипотез R-1..R-10) |

**Гейт E** (заранее зафиксированный):
- политика выбрана на 2026-03..06 и проверена один раз на 2026-07..10 в реплее с исполнением;
- чистое ожидание сделки — нижняя граница 95% > 0;
- средняя дневная выручка > 0;
- ≥ 60% месяцев ≥ 0;
- макс. просадка не хуже X;
- затем ≥ 14 дней теневого портфеля без нарушения.

Если не проходит ни одна политика, чемпион — **«не торговать / минимальная торговля»**, и это
говорится прямо.

### Этап F — автономный контур обучения (задача 7)

- **L1 Аналитик:** разложение дневной выручки (раздел 1) + разбор каждого убыточного дня и каждого
  пропущенного лидера (`incident_analyst.py` расширяется на деньги).
- **L2 Автор гипотез:** формулирует гипотезы по разложению и случаям. Только существующие ключи
  `trader/trader_config.py` (закрывает открытый дефект 2026-08-05), со ссылками на case_id, с проверкой по
  `already_tried.jsonl`.
- **L3 Валидатор:** реплей E1 с заранее записанным критерием, деление по времени, **учёт числа
  попыток** (реестр множественных проверок, §5.2 целевой спеки). Иначе подбор параметров
  находит шум.
- **Подбор параметров** (RM-17, Optuna) — walk-forward по максимальному периоду. Результат —
  гипотезы для L3, а не правки конфига.
- **Продвижение:** L3 accept → теневой портфель → readout → флаг. Целевая спека требует
  одобрения оператора для любых изменений поведения. Для демо (деньги ненастоящие) можно
  разрешить авто-продвижение внутри заранее одобренного конверта: диапазоны параметров + триггеры
  авто-отката по просадке, целостности данных и дневному лимиту. Это **решение оператора**.
- **Аналитика прогресса:** ежедневно — выручка за день/7д/30д с ДИ и бенчмарками; разрыв реплей ↔
  факт; что проверено, принято, откатано; «рано судить», пока ДИ включает 0. Еженедельный отчёт
  не должен изображать еженедельное самоулучшение (§9 целевой спеки).

   каждого изменения.

## 6. Риски

- **Демо ≠ живой рынок.** Цены похожи, но не идентичны; исполнения на демо-стакане оптимистичнее.
  Цифры демо завышают реальную выручку. Замеряется на этапах A/C.
- **Переобучение подбором.** Сотни попыток на одних и тех же 200 днях найдут «прибыльную»
  политику случайно. Защита — деление по времени, учёт попыток, теневые портфели (раздел E/F).
- **Шум метрики.** Дневная выручка не может судить изменения за недели (≈ 2 650 дней на
  +0.10%/день). Судят парные сравнения; дневная выручка — итог.
- **Нестационарность.** impulse_speed был прибылен в марте — начале мая и убыточен потом. Любое
  найденное преимущество нужно перепроверять; авто-откат по заранее записанным триггерам.
- **Инфраструктура:** лимиты API, переподключения WS, техработы демо (ордера нельзя ставить и
  отменять), смещение часов.
