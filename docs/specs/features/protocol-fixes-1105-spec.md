# Исправления протокола проверки гипотез трейдера после внешней ревизии

Дата: 2026-11-05. Решение оператора: «всё по порядку с первого пункта», пункт 3 плана
`docs/audit/review-verification-2026-11-05.md`. Трейдер (`trader/`). Прошлые вердикты не пересматриваются. Правила
действуют для новых расчётов и для readout'ов, которые считаются после этого изменения.

## 0. Что исправляется и почему

| № | дефект | источник |
|---|---|---|
| P1 | Результаты не хранят происхождение данных и кода. Тест H3 от 10-11 не воспроизводится (R −0.2485 → −0.157), и причину нельзя установить | сверка ревизии §3 |
| P2 | **Обрезка у правого края.** `exit_plan` молча закрывает позицию как `time` на последнем баре сетки, если 96 баров удержания не уместились. Сетка обрезана до последнего полного дня UTC (`exit_validator.Grid`). Результат зависит от даты запуска: тест H3 на сетке до 10-11 даёт net −0.188% против −0.164% на полной | найдено 11-05 при поиске причины P1 |
| P3 | Поле `lo95` хранит интервал на 1 − α при любом α (BH19: у FC 95%, у остальных 99%). При малом α граница бутстрапа — одно из 0–2 крайних наблюдений | ревизия S1, S2 |

| P8 | Блок 5 дней задан жёстко; для carry нужен блок ≥ 20 дней | ревизия S3 |

## 1. Требования

**P1. Происхождение данных и кода.** Новый модуль `trader/provenance.py`:
- `code_state()` → `{"head", "dirty"}`: коммит git и признак незакоммиченных правок в `trader/`;
- `file_digest(path)` → sha256 файла, первые 16 знаков;
- `events_digest(path, until)` → sha256 строк `bot_events.jsonl` с полем `ts` < `until` и их число. Файл бота
  растёт, а этот отпечаток для прошлого окна воспроизводим;
- `grid_digest(grid, i0, i1)` → sha256 массивов C/H/L/O сетки на барах [i0, i1);
- `block(**parts)` → словарь `provenance` для записи в результат.

`execution_replay.main` и `cost_calibration.run` пишут `provenance`. Каждая новая спека эксперимента обязана его
писать.

**P2. Обрезка у правого края.**
- `execution_replay.run` помечает сделку `censored = True`, если `reason == "time"`, `exit_ix == grid.N − 1` и
  `exit_ix < ie + max_bars`.
- В результате появляется поле `n_censored`.
- `execution_replay.main` и `_audit_k1_replay_windows` печатают его.
- Окно решения допустимо, только если `n_censored == 0` или результат дан и с этими сделками, и без них.

**P3. Интервалы.** `daily_revenue.aggregate` добавляет `ci_level = 1 − α` и `ci_method`:
- `"block_bootstrap_percentile"` — если `int(α/2 · BOOT) ≥ 20`;
- иначе `"normal_block_se"`: граница = среднее ∓ z(1 − α/2) · SE, где SE — стандартное отклонение блочных
  бутстрап-средних.
- Поля `lo95` / `hi95` остаются под теми же именами (их читают отчёты и readout'ы), а их уровень всегда указан в
  `ci_level`.
- При α = 0.05 и B = 2 000 индекс равен 50, так что ежедневный отчёт и текущие readout'ы с α = 0.05 не меняются.

**P4. PBO.**
- В `pbo.cscv_pbo` ничья (logit = 0) считается как 0.5, а не как переобучение.
- Новая функция `pbo.applicable(R, min_n=6, dup_corr=0.98)`: кандидаты, у которых корреляция дневных рядов ≥ 0.98,
  считаются одним; PBO применим, если различных кандидатов ≥ 6. Если нет, PBO не используется как вето, а пишется со
  статусом `not_applicable`.

**P5. Книга CAP с переоценкой.** `cap.book_marked(baskets, days)` — дневной R книги, в которой каждое событие
держит весь капитал и переоценивается каждый день по `marks` своих пар. Дни перекрытия событий, если они есть,
делят капитал поровну. `experiment_cap` пишет и старую книгу (как было), и `book_marked`, поле `book_marked_agg`.

**P6. Учёт взглядов.** Файл `docs/audit/alpha_ledger.json` — список всех взглядов на отложенные окна
(2026-01-01..; 2018–2022 для BH19): гипотеза, дата, окно, α, исход. Тест `test_protocol_fixes` сверяет, что каждый
маркер `trader/runtime/experiments/*_OPENED.json` есть в журнале. Если каталога нет (чистая копия), тест пропускается.

**P7.** `cap.mean_ci` и `daily_revenue.aggregate` при n < 10 не пишут интервал (`lo95` / `hi95` = None) и ставят
`ci_method = "too_few"`.

**P8.** `daily_revenue.aggregate(..., block=5)` — длина блока становится параметром. Новые carry-спеки задают
`block ≥ 20`.

## 2. Не входит

- Круговой бутстрап (S4): эффект мал, отложено.
- Пересмотр прошлых вердиктов: QB уже закрыт взглядом на 2026, CAP — TOO_FEW, остальные отклонены по нескольким
  критериям.
- Изменение `trading_policy.exit_plan`: его использует только реплей, и обрезка помечается в реплее.

## 3. Тесты (до кода, `trader/test_protocol_fixes.py`)

1. P1: `events_digest` не меняется, если в файл дописаны строки с `ts` ≥ `until`; `grid_digest` меняется при
   изменении цены в окне.
2. P2: сделка, которую срезал край сетки, помечена `censored`; сделка с полным путём — нет.
3. P3: при α = 0.05 метод — перцентильный, `ci_level` = 0.95; при α = 0.05/24 метод — `normal_block_se`, и интервал
   шире перцентильного индекса 2.
4. P4: два одинаковых кандидата → `applicable` = False; ничья не считается переобучением.
5. P5: событие с промежуточной просадкой −20% и итогом +5% даёт в `book_marked` max DD ≤ −15%, а в старой книге — 0.
6. P6: каждый маркер `*_OPENED.json` есть в журнале.
7. P7: n = 2 → интервал None, `ci_method = "too_few"`.
8. P8: `block` передаётся в бутстрап.

## 4. Журнал

### 2026-11-05 — поиск причины P1, тесты до кода, код

**Причина расхождения H3 (P1) найдена частично.**
- Реплей детерминирован: два прогона подряд дают одинаковый хэш сделок `51f068390f8a` (R −0.1569, 869 сделок).
- Политика X4 та же, хэш `0bccb4b2cf6d04f9`. Код реплея после 10-16 менялся только в F2 (выученный выход, X4 его не
  использует). Код 10-11..10-16 в git не попал.
- Обрезка у правого края (P2): сетка, обрезанная на 2026-10-11 00:00 UTC (последний полный день на момент запуска
  10-11), сдвигает net на сделку с −0.164% до −0.188%, R — с −0.1569 до −0.1588, а сделок остаётся 869. Запись от
  10-11: −0.292% и 865 сделок. Обрезка объясняет около 0.02 из 0.13 п.п. разрыва. Остаток **не объяснён**: свечи
  истории, события бота или незакоммиченный код того времени. Проверить это нельзя: хэшей входов не было.
- Попутно найдено: `exit_validator.load_grid` кэширует сетку в глобальной переменной. Если её обрезать, обрезанной
  она остаётся до конца процесса. Это не дефект живого кода, но ловушка для скриптов проверки.

**Тесты.** `trader/test_protocol_fixes.py`, 10 тестов. До кода 10 из 10 падали (7 ошибок, 3 несовпадения). После кода
10 из 10 проходят. Весь набор трейдера — 684 OK. Одна правка после первого прогона: `ci_level` округлялся до 6 знаков,
а спека требует ровно 1 − α. Исправлен код, тест не менялся.

**Код.**
- `provenance.py` (P1). `execution_replay.main` пишет блок `provenance` (код, отпечаток событий до последнего бара,
  отпечаток сетки), `cost_calibration.run` — отпечатки файлов данных.
- `execution_replay.run`: флаг `censored` у сделки и поле `n_censored` (P2). Оно печатается в `main` и в
  `_audit_k1_replay_windows`. Перезапуск K1: на test H3 обрезанных 0, на окне E7 (10-13..11-05) — 10 из 211, на окне
  демо — 10 из 138. Выводы K1 не меняются.
- `daily_revenue.aggregate`: поля `ci_level` и `ci_method`, параметр `block`; нормальная граница с бутстрап-SE, если
  за границей меньше 20 повторов; при n < 10 интервала нет (P3, P7, P8). `paired` передаёт `block`.
  - Живые readout'ы (E7 ≥ 28 дней, FC-SHADOW ≥ 90, W-SHADOW ≥ 30, CAP-SHADOW ≥ 15 событий) и сверка «демо против
    бумаги» (≥ 10 дней) сравнивают `lo95` только после своего минимума и считают при α = 0.05. Их числа не меняются,
    это проверено чтением кода.
- `pbo.cscv_pbo`: ничья = 0.5; `pbo.applicable` (P4).
- `cap.basket` возвращает `marks`; `cap.book_marked`; `cap.mean_ci` без интервала при n < 10;
  `experiment_cap` пишет `book_marked_agg` рядом со старой книгой (P5, P7).
- `docs/audit/alpha_ledger.json`: 17 взглядов, из них 6 с маркерами `*_OPENED.json` (P6). По программе FC_PASSIVE —
  единственный приём, который выдерживает 0.05/17; H3/X4 (z ≈ 2.7) не выдерживает.
