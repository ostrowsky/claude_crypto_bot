# Журнал аудита трейдера: каждый запрос к Binance и каждое решение

Статус: **спека**, кода нет. Дата 2026-10-12. Запрос оператора: «предусмотри логирование всех
взаимодействий бота с Binance и всех принятых решений, это необходимо для дальнейшего анализа
эффективности бота». Приложение: `trader/`, бота не меняет. Порядок: спека → тесты → код.
Правила truth harness: TH-05, TH-09, TH-12, TH-13; CLAUDE.md §0 правило 1 (сначала логирование).

**Охват.** Трейдер — та часть, что общается с Binance и будет торговать на демо-счёте. Сигнальный
бот уже пишет свои решения в `files/bot_events.jsonl` (вход, блокировка с причиной и фильтром,
выход, poll heartbeat). Его HTTP-запросы к Binance не логируются. Это отдельный вопрос и
отдельная спека, если оператор решит: бот без его решения не меняется.

## 1. Зачем

Без журнала нельзя ответить на вопросы, которые будут задаваться всегда:
- почему кандидат не стал сделкой;
- какая доля решений упирается в слоты, кулдаун, фильтр;
- сколько стоит исполнение;
- какие запросы отказывают и как часто;
- какой разрыв между реплеем и фактом.

Сейчас:
- клиент Binance ничего не пишет;
- `trading_policy.decide_entry` в 11 местах возвращает `None` без причины;
- теневой портфель пишет только входы и выходы, а пропуски теряются.

## 2. Два журнала (только дозапись, по UTC-суткам)

| журнал | файл | одна строка = |
|---|---|---|
| **обмен с Binance** | `trader/runtime/audit/exchange/YYYY-MM-DD.jsonl` | один HTTP-запрос (или одна сессия WS API) |
| **решения** | `trader/runtime/audit/decisions/YYYY-MM-DD.jsonl` | одно решение одной книги/исполнителя по одному кандидату или позиции |

Общие поля каждой строки: `schema` (`audit.exchange.v1` / `audit.decision.v1`), `ts` (UTC, мс),
`process` (`recorder` / `equity` / `shadow` / `smoke` / `executor` / …), `run_id` (на запуск
процесса), `app_version` (git HEAD, если доступен).

### 2.1 Обмен с Binance (`ExchangeClient._request`)

Поля:
- что запрошено: `host`, `method`, `path`, `params` — параметры запроса **без** `signature`,
  `apiKey` и заголовка `X-MBX-APIKEY`; `timestamp` и `recvWindow` остаются, они нужны для
  разбора −1021;
- признак `signed`;
- ответ: `status` (HTTP), `ok`, `error_code` и `error_msg` (из ответа Binance, или `network`);
- служебное: `latency_ms`, `bytes`, `used_weight_1m` после ответа, `retry` (повтор после −1021).

**Тело ответа не пишется** по умолчанию: `exchangeInfo` весит 19 МБ, стаканы и тикеры огромны.
Исключение — эндпоинты, где тело и есть решение или деньги: `/api/v3/order*`, `/api/v3/orderList*`,
`/api/v3/account`, `/api/v3/myTrades`, `/api/v3/openOrders`, `/api/v3/order/test`. У них
пишется тело целиком (у `account` — только ненулевые балансы и `canTrade`), а
`clientOrderId`, `orderId` и `orderListId` выносятся в отдельные поля для связки.

Ключ, секрет и подпись не попадают в журнал **никогда**. Проверяется тестом на любом
подписанном запросе и на тексте ошибки.

### 2.2 Решения

Поля:
- `decision_id` — детерминированный хэш (книга, sym, tf, ts события, вид решения), одинаковый при
  повторном прогоне;
- `book` (или `executor`), `policy_epoch`;
- `kind`: `entry_decision` | `exit_decision` | `orphan_exit` | `day_mark`;
- **кандидат:** sym, tf, ts события бота, его ключ (event, sym, tf, ts), цена, режим, оценки
  (`ml_proba`, `candidate_score`, `ranker_final_score`), снимок позиционирования, если есть;
- **состояние:** открыто позиций, занятые символы, капитал, R дня, счётчик дня, кулдаун по символу;
- **итог входа:** `action` ∈ {`enter`, `skip`}, `reason` — один код из списка §3, при `enter` —
  доля, сумма, цена исполнения, издержки, план выхода (стоп и тип);
- **итог выхода:** причина (`real` / `trail` / `time` / `tp` / `sl` / `leader` / `rsi_hold`), бар,
  цена до и после издержек, pnl, удержание в барах;
- для исполнителя этапа C (позже) — ссылка на ордера: `client_order_ids` → те же id в журнале
  обмена.

## 3. Коды причин отказа во входе (`decide_entry`)

`not_bot_entry`, `mode_filtered`, `score_missing`, `score_below_min`, `random_excluded`,
`daily_cap`, `slots_full`, `symbol_held`, `daily_loss_limit`, `cooldown`, `no_stop_distance`,
`zero_size`.

Плюс отказы движка, до или после `decide_entry`:
- `no_price`;
- `off_grid` — нет свечей для символа;
- `no_exit_plan`;
- `notional_too_small`;
- `no_bars` — нет закрытого бара на момент входа.

**`decide_entry` не меняет поведения.** Новая функция `decide_entry_explained` возвращает
`(frac | None, reason)`. `decide_entry` вызывает её и возвращает только `frac`. Паритетные тесты
E1/E7 должны остаться зелёными: логирование не меняет ни одного решения.

## 4. Где включается

| процесс | журнал обмена | журнал решений |
|---|---|---|
| `microstructure_recorder`, `equity_snapshots`, `_smoke_demo_connection`, `trading_universe` | да (через клиент) | — |
| `shadow_portfolio step` | да (klines) | да: каждое событие × каждая книга, + `day_mark` |
| `execution_replay`, эксперименты | нет по умолчанию (офлайн, миллионы решений) | по флагу `--audit` в отдельный каталог `audit/replay/<run_id>/` |
| исполнитель этапа C (будущий) | да | да, с `client_order_ids` |

Флаги в `trader/trader_config.py`:
- `AUDIT_EXCHANGE_ENABLED = True`, `AUDIT_DECISIONS_ENABLED = True`;
- `AUDIT_RETENTION_DAYS = 0` — 0 = хранить всё, удаления нет.

**Объём:** рекордер — около 180 запросов на снимок, примерно 52 тыс. строк и около 15 МБ в сутки.

## 5. Надёжность

- **Сбой записи журнала не ломает работу:** запрос и решение выполняются. Ошибка записи
  считается в счётчике процесса и раз в шаг печатается в лог. Для исполнителя этапа C позже
  решится отдельно, не ставить ли ордер без записи (fail-closed).
- **Запись:** одна строка — один `write` с `\n` в режиме дозаписи. Файл не переписывается.
  Сутки — по UTC.
- **Время** в мс UTC. Задержка `latency_ms` — от отправки до конца чтения тела.

## 6. Анализ

`trader/audit_report.py --days N` печатает сводку:
- по обмену: запросы, ошибки и доля по эндпоинтам, задержка p50/p95, вес;
- по решениям: число входов и пропусков по книгам, распределение причин пропуска, выходы по
  причинам, средний pnl по причине.

Это основа для анализа эффективности: при каком фильтре теряется доход и где именно сделки
дешевле или дороже по исполнению.

## 7. Требования к коду (тесты до кода)

1. **Каждый запрос клиента** даёт ровно одну строку обмена с полями §2.1, включая неудачные:
   HTTP-ошибка с кодом Binance, сетевая ошибка (`network`), срок запроса (`deadline`). Повтор
   после −1021 — отдельная строка с `retry = true`.
2. **Секреты:** ни в одной строке нет ключа, секрета, подписи, `X-MBX-APIKEY` — ни при успехе, ни
   при ошибке, ни в тексте исключения.
3. **Тело ответа:** пишется только для эндпоинтов из списка §2.1. `exchangeInfo`, `depth`,
   тикеры, `klines` — без тела, с полем `bytes`.
4. **Сбой записи** (каталог только для чтения) не прерывает запрос и решение.
5. **Ротация по UTC-суткам:** строки после 00:00 UTC идут в файл новых суток.
6. **`decide_entry_explained`:** каждый код §3 возникает на своём случае; `decide_entry` даёт тот
   же результат, что и раньше, на всех существующих тестах.
7. **Теневой движок:**
   - на каждое событие входа пишется по одной строке решения на книгу (`enter` или `skip` с
     причиной);
   - на каждый выход — строка с причиной и ценами;
   - `day_mark` — раз в сутки на книгу;
   - паритет с реплеем (E7 §5) не меняется.
8. **`decision_id`** одинаков при повторной обработке того же события и разный у разных книг.
9. **`audit_report.py`:** на синтетических журналах считает доли ошибок, p50/p95 задержки и
   распределение причин.
10. **Границы:**
    - запись только в `trader/runtime/audit/`;
    - журналы только дозаписываются;
    - в `files/` и `.runtime/` бота ничего не пишется.

## 8. Ход работы — 2026-10-12

**Тесты** — `trader/test_audit_log.py`:
- 12 тестов §7 написаны до кода, все упали на старом коде;
- одна правка в тесте после кода: помощник читал все `*.jsonl` во временной папке, включая файл
  входных событий. Теперь он читает только каталог `decisions`;
- всего тестов трейдера 119, все проходят, паритет E1/E7 не изменился.

**Код:**
- `trader/audit.py` — писатель, коды, `decision_id`;
- `exchange_client._request` — одна строка на запрос, включая ошибки, `network`, `deadline` и
  повтор после −1021;
- `trading_policy.decide_entry_explained` — `decide_entry` вызывает её, поведение то же;
- `shadow_portfolio.ShadowEngine` — `entry_decision` (enter/skip с причиной), `exit_decision`,
  `orphan_exit`, `day_mark`;
- `trader/audit_report.py` — сводка.

Имя процесса задаётся в точке входа: `recorder`, `equity`, `shadow`, `smoke`, `universe`.
`run_tests.py` выключает запись в настоящий журнал (`TRADER_AUDIT_DISABLED=1`): тесты аудита
пишут во временные каталоги.

**Первые данные (16:26–16:37 UTC):**
- 222 строки обмена, ~85 КБ;
- 207 запросов стакана, 9 тикеров, 3 `time`, 3 `account`;
- 89 строк с `process = unknown` — это запуск, начатый до правки имён процессов.

Журнал решений появится с первым событием бота или с отметкой 00:00 UTC.

**Ограничения:**
- `app_version` — последний коммит (`git rev-parse HEAD`). Незакоммиченные изменения рабочей
  копии он не отражает. Решения однозначно описывает `policy_epoch`.
- **HTTP-запросы сигнального бота не логируются** — нужна отдельная спека и решение оператора.
