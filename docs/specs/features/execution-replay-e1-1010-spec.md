## 1. Зачем

Каждая гипотеза этапов E–F («меньше сделок», «другой выход», «дневной лимит убытка», «размер по
волатильности») должна оцениваться в деньгах: комиссии, проскальзывание, размер позиции, слоты,
дневная выручка. Сейчас движков два, и денег нет ни в одном:
- `exit_validator.py` — разница pnl на сделку без комиссий и без портфеля;
- `goal_validator.py` — пойманные дни-победители.

Базовая линия (`_backtest_daily_revenue_baseline.py`) — разовый скрипт: только реализованный
результат, фиксированные слоты, без проскальзывания. E1 — один движок, по которому дальше судятся
все денежные гипотезы.

## 2. Контракт «одна функция решения» (против расхождения обучение ↔ факт)

```python
# files/trading_policy.py
@dataclass(frozen=True)
class TradingPolicy:
    name: str
    admission: AdmissionRule        # кандидат + состояние портфеля -> входить ли
    sizing: SizingRule              # -> доля капитала / USDT
    exits: ExitRule                 # -> TP, SL, трейл, лидер, выходы по слабости, таймаут
    risk: RiskLimits                # слоты, кластер, кулдаун, дневной лимит убытка, аварийный стоп
    def epoch(self) -> str: ...     # sha256 параметров = policy_epoch (§3.4b целевой спеки)

def decide_entry(policy, candidate, state) -> EntryDecision | None
def decide_exit(policy, position, bar, state) -> ExitDecision | None
```

Этот же модуль вызывает исполнитель этапа C (`order_manager.py`). Реплей и живая торговля
различаются только источником баров и модулем исполнения: `fill_model.py` в реплее,
`exchange_client.py` вживую. Логика решения у них общая. Тест-контракт: на одном и том же наборе
баров и кандидатов реплей и paper-режим этапа C дают одинаковые решения (`test_policy_parity.py`).

## 4. Модель исполнения (`trader/fill_model.py`, общий с paper-режимом этапа C)

| событие | цена исполнения | комиссия |
|---|---|---|
| рыночная покупка по сигналу | `p_signal × (1 + half_spread + impact(size))` | taker |
| вариант чувствительности «задержка» | открытие следующего бара × (1 + half_spread + impact) | taker |
| TP (лимит на продажу) | TP, только если `high ≥ TP × (1 + 1 тик)`: нужна сделка сквозь уровень, без оптимизма по очереди | maker |
| SL (stop-limit на бирже) | срабатывает при `low ≤ stop`; цена = `min(stop, open бара)` × (1 − half_spread − impact): гэп ниже стопа исполняется по открытию | taker |
| TP и SL в одном баре | **сначала SL** (пессимистично) | — |
| выход бота (трейл, лидер, слабость, таймаут) | решение на закрытии бара, `close × (1 − half_spread − impact)`; вариант — следующее открытие | taker |

**Исправлено 2026-10-10, до использования результатов:** первый вариант (5 б.п. + `k = 0.1` от
объёма бара 15m) брал ~1.4% на сторону, примерно в 100 раз больше измеренного стакана. Временные
уровни взяты из первых двух снимков A0 (демо-стакан, 42 пары; ордер 1 000 USDT стоит от mid
6.6 / 10.0 б.п. покупка/продажа по медиане и 20–23 б.п. по p90): **0 / 8 / 20 б.п. на сторону**,
без члена размера, до калибровки по паре через 7 дней A0.
`impact(size) = k × sqrt(size_usdt / quote_vol_15m)` — закон квадратного корня. `half_spread` и
`k` калибруются по A0 для каждой пары и часа суток. **До калибровки** каждый результат печатается
при трёх уровнях: 0, `half_spread = 5 б.п., k = 0.1` и удвоенном. Вывод «прибыльно» допустим,
только если он держится при среднем уровне. После этапа C модель перекалибровывается по
фактическим исполнениям демо (разрыв реплей ↔ факт, метрика §6).

## 5. Портфель (`trader/execution_replay.py`)

- Событийный проход по барам 15m. Состояние: кэш USDT, позиции (кол-во, цена входа, стоп,
  TP, режим, бары удержания), кулдауны, счётчики дня.
- **Переоценка по закрытию каждого бара.** Капитал в 00:00 UTC → R_d считается **той же функцией
  `daily_revenue.aggregate()`**, что и метрика демо-счёта. Реплей и факт сравниваются одним кодом.
- Размер: равные слоты (1/N) | риск r% капитала / дистанция до SL с потолком на позицию | фиксированная сумма.
- Ограничения: `MAX_OPEN_POSITIONS`, кластер корреляции (`correlation_guard`), кулдауны бота,
  минимальный notional и округление количества (фильтры как на бирже, заглушка до гейта A),
  дневной лимит убытка, аварийный стоп по просадке.
- Кандидат при занятых слотах пропускается. Ротация (`rotation.py`) — отдельная политика, по
  умолчанию выключена в v1. Иначе нельзя воспроизвести базовую линию.

## 7. Протокол оценки гипотез (L3 в деньгах), зафиксирован сейчас

- **Чемпион:** политика «как вживую» (входы и выходы бота по логу, равные слоты). Рядом всегда
  печатается **«кэш»** (R = 0).
- **Деление по времени:** выбор параметров и вариантов — на днях < 2026-07-01, проверка **один
  раз** на днях ≥ 2026-07-01. Подбор с многими вариантами — walk-forward, 4 окна по времени.
- **Парная разница** `R_d(кандидат) − R_d(чемпион)` в одни и те же дни, блочный бутстрэп
  (блок 5 дней).
- **Вердикт `improves`:**
  - нижняя граница парной разницы > 0 на проверке;
  - макс. просадка не хуже чемпиона более чем на 5 п.п.;
  - ≥ 60% месяцев проверки с разницей ≥ 0;
  - ≥ 200 сделок кандидата на проверке.
- **Вердикт `profitable`** (гейт E дорожной карты):
  - средняя R кандидата > 0;
  - нижняя граница чистого ожидания сделки > 0;
  - оба при среднем уровне проскальзывания.
- **Учёт попыток:** каждый кандидат, оценённый на проверке, пишется в
  `trader/runtime/experiments/trials.jsonl` (семейство, параметры, epoch, хэши входных данных).
  Граница считается на уровне `1 − 0.05/k`, где k — число кандидатов семейства, открытых на
  проверке (Бонферрони; §5.2 целевой спеки). Выбор — только на обучающей части.
- Отрицательный результат пишется в `already_tried.jsonl` с цифрами (TH-08).

Модуль `trader/money_validator.py` реализует этот протокол. Он подключается к L3 рядом с
`goal_validator` и `exit_validator`, а не вместо них: цели раннего входа остаются диагностикой.

## 8. Первое семейство гипотез (после V1–V5; зарегистрировать до запуска)

| # | кандидат | вопрос |
|---|---|---|
| H0 | «кэш» и чемпион | контроль: чемпион ≈ −0.83%/день на V1-условиях; с проскальзыванием хуже |
| H1 | комиссия BNB | сколько даёт одна скидка (по базе ≈ +0.14%/день) |
| H2 | top-k кандидатов в день по `ml_proba` / `ranker_final_score` / `candidate_score`, k = 1, 3, 5 | меньше сделок — меньше комиссий. Бюджет алертов был опровергнут **по раннему входу** (10-01), по деньгам не проверялся |
| H3 | выходы: X-9c (режим лидера), удержание после дивергенции RSI при прибыли ≥ +0.5%, широкий трейл 8% на ракетоподобных | захват движения — слабый множитель |
| H4 | TP/SL на бирже (OCO) лестницей: TP = 1.5/2/3 ATR, SL = 1/1.5 ATR | замена выхода бота на биржевой |
| H5 | фильтр режима: нет новых входов при BTC ниже EMA50 и/или отрицательной ширине рынка | дни, в которые не надо торговать |
| H6 | дневной лимит убытка −1/−2/−3% | хвост худших дней |
| H7 | размер по риску (0.5/1% на сделку) против равных слотов | тот же сигнал, другая выручка |

Каждый кандидат выбирается на обучающей части. На проверку идёт по одному победителю на строку.
k для поправки — число строк, открытых на проверке.

## 11. Что E1 не делает

- Не меняет живой бот: только чтение логов и истории. Откат не нужен, shadow не применим.
- Не оценивает новые правила входа (E1b) и не обучает модели (E2).
- Не заменяет демо: цифры реплея — оценка сверху до калибровки проскальзывания по фактическим
  исполнениям (V6).

Максимальный период: все дни с 2026-03-01 (кандидаты с признаками в логе), деление по времени из
§7. Расширение назад невозможно: события `blocked` с признаками раньше этой даты не логировались.
Это ограничение указывается в каждом пакете.
