## 1. Разбор упущенных лидеров — `files/incident_analyst.py`

Каждый день (шаг `incidents` в `pipeline_run.py --daily`, до `notify`) по каждому
победителю вчерашнего дня — неизменный top-20 биржи (глобальный ранг, потом
watchlist, знаменатель North Star) — определяется ПЕРВОЕ место, где бот его
потерял. Порядок детерминированный:

`bot_down` (бот < 18 ч — нет данных, не промах) → `held_from_before` →
`caught_early` (вход до первого закрытия 15m ≥ +2.5% от открытия UTC — цель) →
`caught_late` → `blocked` (первый фильтр) → по журналу опроса:
`rule_fired_no_candidate` / `no_rule_fired` (причины правил) / `cooldown` /
`not_polled` / `data_gap` / `no_heartbeat`.

Для взятых — выход: pnl, класс выхода, захват (pnl / ход дня), рост после выхода
в тот же день, переключение в режим лидера. Ранжирование — `missed_pct` = ход дня
минус реализованный pnl. Бары дня берутся с Binance (15m, 96 баров): времена
пересечения из хранилища меток строятся по 1h-истории и отстают на день.

LLM (роль Analyst, `continuous-improvement-agent-spec.md` §4.1) только
группирует случаи по механизму, обязан ссылаться на case_id; группы с
несуществующими id отбрасываются, формулировки-«рецепты» помечаются
(`remedy_wording`). Классификацию LLM не меняет.

Выход: `.runtime/pipeline/incidents/<day>.json`; блок «Лидеры <день>» в утреннем
сообщении; `rollup(14)` уходит в L2 как `incidents_14d`.

## 2. Валидатор по цели в L3 — `files/goal_validator.py`

Для ключей, которые L3 умеет воспроизводить (TQ, chop, ML floor), вердикт выносит
критерий проекта — тот же, что в ручных P-проверках с 2026-09-25:

- **цель:** доля дней-победителей (неизменный top-20, бот весь день, пересечение
  известно), где бот вошёл ДО первого +2.5%; при ослаблении — ожидание
  `now + Σ 1-(1-p)^k` (p — доля кандидатов, прошедших фильтр, ставших входом);
  при ужесточении — дни, где удалены все ранние входы;
- **сделка:** откалиброванный live_trail (P-1), обе руки от бара решения, пол
  трейла по режиму; 95% интервал (объединённое − текущее), граница неухудшения
  −0.10 п.п.; разбивка по месяцам;
- **период:** maximum available — с 2026-05-01 (текущий набор фильтров и калибровка
  P-1), для ML — с 2026-09-07 (шкала модели).

Правила (зафиксированы до оценки гипотез):

| | accept | reject |
|---|---|---|
| relax | цель ≥ +0.5 п.п. И низ ≥ −0.10 И ≥ 50% месяцев за | цель ≤ 0 ИЛИ низ < −0.10 |
| tighten | потеря цели < 0.5 п.п. И низ > 0 | потеря ≥ 0.5 п.п. ИЛИ верх < 0 |

`needs_data` при < 30 днях-победителях или < 20 сделок в любой руке; иначе
`needs_review`. Пиковый вердикт хранится рядом (`peak_replay`), не усредняется.
Решает цель; если валидатор цели упал — остаётся пиковый с пометкой.

## 3. Гипотезы о выходе и режиме лидера — `files/exit_validator.py` (2026-09-29, «делай 3»)

До этого L3 не умел проверить ни один ключ выхода, поэтому агенту их не
предлагали, и сторона выхода — где бот оставляет ~92% хода ракеты — была вне
цикла. Каждое изменение выхода (X-7b, X-9c, трейл alignment) проверялось вручную
скриптом `_backtest_leader_x8_x9.py`. Теперь это третий валидатор L3.

**Ключи.** Режим лидера: `LEADER_EXIT_RANK_MAX`, `_MIN_RET`, `_FLOOR_PCT`,
`_LOST_RANK`, `_LOST_MIN_BARS`, `_MAX_HOLD_BARS`. Пол трейла по режиму:
`TRAIL_MIN_BUFFER_PCT_<MODE>` (7 режимов).

**Движок.** Каждая реальная 15m-сделка с выходом с 2026-03-01 (maximum period
15m-хранилища, 4 286 сделок) проигрывается при текущих и предлагаемых
параметрах. Ключи лидера — тем же правилом, что `leader_exit.step` (ранг по
доходности от открытия UTC среди watchlist, широкий трейл от бара
переключения, выход по потере топ-N, лимит удержания); без переключения
остаётся реальный выход. Сделка, вышедшая в режиме лидера вживую (с 27.09), у
которой в одной из версий нет переключения, не имеет наблюдаемого старого
выхода — исключается из обеих рук и считается (`unobservable`). Ключи пола —
обе руки на откалиброванном трейле P-1 от бара входа (96 баров), только сделки
этого режима; мягкие выходы (WEAK, RSI) движок не моделирует — ограничение,
одинаковое для обеих рук.

**Критерий (зафиксирован до прогона гипотез).** Парная разница (новое − текущее)
по сделке, bootstrap 95%:

| | правило |
|---|---|
| accept | ракетные дни: низ > 0 И все сделки: низ ≥ −0.10 п.п. И ≥ 60% месяцев (≥ 5 ракетных сделок) ≥ 0 |
| reject | все сделки: низ < −0.10 ИЛИ ракетные дни: верх < 0 ИЛИ ни одна сделка не меняется |
| needs_data | < 30 сделок ракетных дней, < 200 сделок или < 30 изменённых сделок |
| needs_review | иначе |

Ракетный день — из неизменного хранилища меток (максимум дня ≥ +10% от
открытия, закрытие удерживает ≥ 60% роста). Рядом — разница на днях-победителях
и охват: доля ракетных дней (watchlist, бот весь день) в режиме лидера.

**Регрессия с ручным бэктестом.** X-9c против X-7b на этом движке: ракетные дни
**+0.45 п.п. [+0.22, +0.73]** (n=360; спека X-9: +0.42 [+0.19, +0.68]), все
сделки −0.003 [−0.034, +0.028] (спека −0.008 [−0.038, +0.023]), переключено 1 096

## 5. trend-scout применяет только по «accept» L3 — `TREND_SCOUT_AUTO_APPLY_REQUIRES_L3`

Аудит «учится ли бот сам» (2026-09-29) нашёл единственный контур, который сам
меняет конфиг: trend-scout в RL-воркере каждые 4 часа. Его критерий — прокси:
средний ret5 ≥ 0 и доля прибыльных ≥ 40% у входов, которые добавил бы новый
порог, на окне 4 часа. Не цель бота и не maximum period (§0a правила 3, 11).
Так `CLONE_SIGNAL_GUARD_MAX_SIMILAR` дошёл с 4 до 23 (последний шаг 22 → 23 —
29.09). Scout пишет прямо в `config.py`, в обход разделения хранилищ; действует
с перезапуска бота.

Теперь `apply_approved_changes` применяет изменение, только если L3-валидатор,
умеющий воспроизвести ключ, вернул `accept` на максимальном периоде:
`goal_validator` для ключей фильтров, `exit_validator` для ключей выхода. Ключи,
которые никто не воспроизводит (из 13 правил scout — все, кроме
`ML_GENERAL_HARD_BLOCK_MIN`), не применяются: они записываются в
`trend_scout_changelog.jsonl` с `held: true` и видны в отчёте scout как «Не
применено — нет подтверждения по цели». Вердикт кэшируется на 7 дней
(`.runtime/trend_scout_l3_cache.json`) — проверка длится минуты, а scout
запускается каждые 4 часа. Без конфига — fail closed. Rollback:
`TREND_SCOUT_AUTO_APPLY_REQUIRES_L3 = False` (прежний прокси-путь). Действует
после перезапуска RL-воркера.

Следствие, сказанное прямо: scout почти перестаёт сам менять конфиг. Это не
потеря обучения, а отказ от изменений без доказательства; уже сделанный дрейф
(`CLONE_SIGNAL_GUARD_MAX_SIMILAR` = 23) не откатывается автоматически —
решение оператора.

## 6. Шлюз замены ночной ML-модели — `files/ml_promotion_gate.py`, `ML_PROMOTION_GATE_ENABLED`

`daily_learning` каждую ночь переобучал `ml_signal_model.json` и перезаписывал
живой файл без сравнения с моделью, которую тот заменяет (тренер выбирает лучшее
из трёх семейств на своей валидации — и всё).

**Сравнение.** На TEST-части тренера — последние 15% строк по времени. Кандидат
их не видел (обучение — первые 70%), вчерашняя модель тоже (её обучающая часть
кончается раньше 85%-й отметки сегодняшних строк). Метрики, парный bootstrap по
строкам, 500 повторов:

- A — AUC по метке, на которую модель учится (пиковая метка);
- B — полнота на ЖИВОМ пороге (`ML_GENERAL_HARD_BLOCK_MIN`, на бычий день —
  `..._BULL_DAY_MIN`): сколько будущих движений фильтр пропустит;
- C — точность на живом пороге.

**Решение.** Оставить прежнюю, если верхняя граница разницы (новая − прежняя) < 0
по любой из трёх (явно хуже). Иначе — заменить, в том числе при ничьей: модель не
замораживается (§0: обучение — P0). Без прежней модели, при другой версии метки
или выборке < 100 строк — заменить без шлюза, с пометкой.

**Критерий C добавлен ПОСЛЕ первого прогона** — сказано прямо, потому что это
нарушение предрегистрации (TH-08/TH-12), сделанное из-за найденного дефекта, а не
чтобы подогнать ответ. Первый прогон (полное ночное обучение на копии, 29.09,
870 строк, база 0.2425): AUC 0.661 → 0.673 [−0.010, +0.035], полнота 0.79 → 0.91
[+0.078, +0.168] — по A и B «заменить». Но кандидат пропускал 82% строк вместо
62%: шкала вероятностей сдвинулась относительно фиксированного порога 0.15, и
полнота росла от «пропустить почти всё»; точность упала 0.308 → 0.271
[−0.055, −0.018]. С C шлюз оставляет прежнюю модель.

**Найденный дефект, не исправленный здесь:** порог ML-фильтра фиксирован, а шкала
модели меняется каждую ночь. Правильно — калибровать порог под модель (как
`bonus_threshold` у top-gainer). Это изменение поведения; нужна своя проверка по
цели.

Журнал решений: `.runtime/ml_promotion_log.jsonl`; отвергнутый кандидат —

## 7. Порог ML под модель — в SHADOW (`ML_FLOOR_CALIBRATION_ENABLED = False`)

Оператор: «откалибруй порог ML под модель». Дефект из §6: порог фильтра
фиксирован (0.15), а шкала вероятностей меняется от модели к модели — блэкаут
20.08 и кандидат 29.09 (пропуск 62% → 82%) — одно и то же.

**Предложение.** Порог задаётся рабочей точкой — «пропускать долю R будущих
движителей» (пиковая метка) — и переводится в число для каждой модели на её
отложенных строках (`ml_signal_model.calibrate_floor`).

**Проверка walk-forward (maximum period `ml_dataset`, 5 800 строк 24.03–29.09,
база 0.160), `files/_backtest_ml_floor_calibration.py`.** Модель обучается
производственным тренером только на строках ДО среза, порог калибруется на её
тестовой части, оценка — на следующих 10% строк, которых модель не видела.
Решающее правило записано до прогона: допустимы R, достигающие не меньше
дней-победителей (вход-кандидат до +2.5% прошёл бы фильтр), чем фиксированный
порог; из них — наибольшая точность.

| | полнота | пропуск | точность | дней-победителей |
|---|---|---|---|---|
| фикс. 0.15 | 0.839 | 0.616 | 0.284 | 17/27 = 63.0% |
| R = 0.80 | 0.804 | 0.557 | **0.301** | 18/27 = 66.7% |
| R = 0.85 | 0.849 | 0.619 | 0.286 | 18/27 |
| R = 0.90 | 0.880 | 0.690 | 0.266 | 19/27 |
| R = 0.95 | 0.928 | 0.787 | 0.246 | 23/27 = 85.2% |

По правилу выбран R = 0.80. **Но посылка не подтвердилась:** фиксированный
порог держал полноту 0.80–0.86 по всем четырём срезам, а откалиброванные пороги
промахивались мимо своей цели на 10–14 п.п. (порог, найденный на тестовой части,
плохо переносится на следующий месяц). Прирост по цели — один день из 27, в
пределах шума. Сдвиг шкалы 29.09 (catboost) срезы не воспроизвели: во всех
четырёх выигрывала логистическая модель.

**Вердикт: не доказано → SHADOW, не живой порог** (§0a правила 7, 10). Тренер
пишет в модель блок `calibration` (порог при R = `ML_FLOOR_TARGET_RECALL` = 0.80
и сетка 0.80–0.95); если шлюз §6 оставляет прежнюю модель, её порог
пересчитывается на свежих строках, которых она не видела. Бот при загрузке модели
пишет событие `ml_floor_calibration` (порог модели рядом с живым). Живой фильтр
использует откалиброванный порог только при `ML_FLOOR_CALIBRATION_ENABLED = True`,
с ограничением [0.02, 0.60] — чтобы калибровка не могла ни закрыть фильтр
наглухо, ни открыть его полностью.

**Проверка тени — `ML-FLOOR-SHADOW` в реестре** (срок 2026-10-21, ≥ 14 дней,
≥ 100 строк): на всех кандидатах, дошедших до ML-фильтра (заблокированы им, позже
или вошли; по одному на монету-час, логированный `ml_proba`), сравниваются
фиксированный и откалиброванный порог — полнота, точность, дни-победители.
KEEP (включить) — если калиброванный достигает не меньше дней и точность не ниже;
меньше дней — остаётся фиксированный. Проверка механики на реальных 26–28.09 с
подставленным порогом 0.20: 562 строки, база 0.208; точность 0.337 против 0.280,
но дней 1 против 2 → фиксированный — пример, не результат.

**Найдено попутно (TH-13, исправляет прежнее утверждение; с §8 — исправлено):** бот загружал
ML-модель ОДИН раз при старте (`monitor._load_ml_model_payload` кэширует навсегда).
Ночное переобучение меняет файл, а в живом фильтре остаётся модель на момент
запуска. Бот запущен 2026-09-28 22:14 — модель 29.09 он не использует. Порог и
модель поэтому всегда из одного файла, что для калибровки правильно; тень начнёт
собирать данные после ближайшего перезапуска с моделью, у которой есть блок
`calibration` (первая такая — ночное обучение 30.09).

Тесты: `files/test_ml_floor_calibration.py` (13).

## 8. Перечитывание ML-модели без перезапуска — `ML_MODEL_HOT_RELOAD_ENABLED`

Оператор, 2026-09-29: «да, сделай перечитывание модели без перезапуска» (после
находки §7: модель читалась один раз на процесс, ночное обучение доходило до
фильтра только при перезапуске).

`monitor._maybe_reload_ml_model` — не чаще раза в `ML_MODEL_RELOAD_CHECK_SEC`
(60 с) сравнивает mtime `ml_signal_model.json` с загруженным. Файл, изменённый
меньше `ML_MODEL_RELOAD_MIN_AGE_SEC` (10 с) назад, может ещё записываться — ждёт
следующей проверки. Нечитаемый или неполный файл (нет `feature_names`/`model`)
не заменяет модель в работе; проверка повторяется. При замене — событие
`ml_model_reload` (старая → новая) и `ml_floor_calibration`, сброс кэша catboost
(по бустеру за ночь не копится), сброс предупреждения о версии метки. Что попадает
в файл, решает шлюз §6. Rollback: `ML_MODEL_HOT_RELOAD_ENABLED = False` + restart.

**Проверка `ML-HOT-RELOAD`** (реестр, срок 2026-10-14): замены были; аномалия —
сразу — если в UTC-день с ≥ 50 кандидатами у ML-фильтра он блокирует ≥ 85% (или
файл модели изменён > 24 ч назад без события перезагрузки). Порог 0.85 выбран
ПОСЛЕ просмотра данных (TH-12), по известному инциденту: первая версия правила
(0.95) на реальном блэкауте 20.08 не сработала бы — по монето-часам в тот день
заблокировано 88.6% из 420, а не 100% (часть кандидатов дня прошла до смены
модели). На 98 днях с июня (≥ 50 кандидатов) правило 0.85 срабатывает ровно на
20.08; следующий по величине день — 0.791 (13.06), медиана 0.215.

Тесты: `files/test_ml_hot_reload.py` (12). Действует после одного перезапуска
бота (новый код `monitor.py`).

## 9. Утренний отчёт не дошёл 2026-10-01 — регрессия этой работы, исправлена

Блоки «Лидеры» и «Проверки изменений» (§1, §4) удлинили утреннее сообщение до
3 963 символов при пределе 4 000. Старая обрезка резала текст посреди HTML-тега
(в конце остался «<»), Telegram отклонил всё сообщение (HTTP 400): 01.10 оператор
не получил ни отчёта о здоровье, ни блоков агента. Шаг `notify` при этом вернул 0 —
журнал писал только «no chats reached; errors=1», без ответа Telegram.

Исправление (`files/pipeline_notify.py`): отчёт собирается из частей
(`_message_parts`) и уходит несколькими сообщениями по границам частей
(`split_for_telegram`); одна слишком длинная часть обрезается `safe_truncate` —
по границе строки, без оборванного тега, открытые `<b>/<i>/<code>` закрываются.
Ошибка Telegram (часть, код, ответ) теперь печатается в журнал. Отчёт за 01.10
отправлен повторно вручную (2 сообщения, 3 713 + 341 символ). Тесты:
`files/test_notify_split.py` (8).
