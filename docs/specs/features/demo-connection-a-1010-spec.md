## A0. Запись микроструктуры (начать сейчас)

**Зачем.** В истории (`history/*_15m*.csv`) есть только OHLCV: ни спреда, ни глубины стакана, ни
оборота в USDT. Без них реплей E1 не умеет считать проскальзывание. Без сравнения демо-стакана с
живым рынком нельзя решить, по какой ленте торговать (этап B). По §0 правило 1 недостающие данные
собираются в первую очередь, и чем раньше начнётся запись, тем раньше их хватит.

**`trader/microstructure_recorder.py`** — отдельный процесс по образцу `positioning_recorder.py`,
со своим запуском `trader/run_recorder.cmd`.
- Каждые `MICRO_RECORD_INTERVAL_SEC = 300` секунд для двух площадок, живой рынок
  `api.binance.com` и демо `demo-api.binance.com` (публичные эндпоинты; работают ли они на демо
  без ключа, проверяется первым запуском):
  - `GET /api/v3/ticker/bookTicker` по всем парам одним запросом: bid, ask, количества;
  - раз в час `GET /api/v3/ticker/24hr` по всем парам: оборот в USDT (`quoteVolume`), число
    сделок;
  - `GET /api/v3/depth?limit=20` по парам кандидатов в универсум, ротацией так, чтобы весь
    универсум обходился за час. Из стакана считается стоимость исполнения рыночного ордера на
    100 / 500 / 1 000 / 5 000 USDT в б.п. от mid (покупка и продажа).
- Запись — **только дозапись**: `trader/runtime/microstructure/YYYY-MM-DD.jsonl`, один файл на сутки
  (урок 08-04).
- Бюджет веса запросов ≤ 10% лимита. Лимит читается из `rateLimits` в `exchangeInfo` и
  контролируется по заголовкам `X-MBX-USED-WEIGHT-*`, не зашивается в код. Ответ 429 → пауза на
  `Retry-After`, 418 → остановка записи до следующего часа и запись в лог.
- Флаг `MICROSTRUCTURE_RECORDER_ENABLED = True` (только запись; откат — False).

**Что получаем через 7 дней:**
1. распределение спреда и стоимости исполнения по парам и часам суток;
2. расхождение mid демо − mid живого рынка по каждой паре (б.п., медиана и p95);
3. оборот в USDT по паре.

Этого хватает, чтобы выставить пороги фильтра ликвидности (A1) и откалибровать модель
проскальзывания E1.

**Тесты** `test_microstructure_recorder.py`:
- стоимость исполнения по синтетическому стакану считается верно;
- лимиты читаются из `exchangeInfo`;
- при 429 запись ставится на паузу;
- файл только дозаписывается.

## A1. Подписанный клиент демо-счёта

### Ключ (делает оператор)

1. demo.binance.com → Binance Demo Trading → API Management → создать ключ (system-generated,
   HMAC).
2. Права: только **Spot & Margin Trading → Spot**, без вывода средств. Ограничение по IP.
3. Записать в `files\.env`: `BINANCE_DEMO_API_KEY=...`, `BINANCE_DEMO_API_SECRET=...`. Файл в
   `.gitignore` (проверено: строки `.env`, `*.env`). Парсер срезает пробелы вокруг `=`.
   **Состояние на 2026-10-10:** обе переменные записаны оператором (по 64 символа, формат HMAC;
   проверены только имена и длина, значения не читались). Клиент читает **только** имена с
   `DEMO` — переменная без `DEMO` могла бы содержать боевой ключ.
4. Что ключ именно от демо-счёта, подтверждает смоук-тест: подписанный запрос уходит только на
   демо-хост (защита ниже), а боевой ключ демо-API отвергает (ошибка −2015). Отказ = ключ не
   от демо-счёта, работа останавливается.

Claude ключ не видит и не вводит. Клиент никогда не пишет в лог ключ, подпись и заголовки запроса.
Перед записью в лог запрос проходит через `redact()`.

### `trader/exchange_client.py`

**Защита площадки (вне конфига):**

```python
ALLOWED_HOSTS = frozenset({"demo-api.binance.com", "demo-ws-api.binance.com", "demo-stream.binance.com"})
```

Подписанный запрос на любой другой хост → `RuntimeError` до отправки. Флага, разрешающего
mainnet, **нет**. Переход на реальные деньги — новая спека и правка этой константы в коде с
решением оператора. Публичные запросы к `api.binance.com` разрешены только без подписи (рекордер,
признаки).

**Подпись и время:**
- HMAC-SHA256 над строкой запроса;
- `timestamp` = локальное время + смещение от `GET /api/v3/time`, пересчёт каждые 10 минут и при
  ошибке −1021;
- `recvWindow = 5000`.

**Методы этапа A** (чтение + сухой прогон):

| метод | эндпоинт | зачем |
|---|---|---|
| `server_time()` | `GET /api/v3/time` | смещение часов |
| `exchange_info()` | `GET /api/v3/exchangeInfo` | пары, статус, разрешённые типы ордеров, фильтры, `rateLimits`; кэш на сутки + при ошибке фильтра |
| `account()` | `GET /api/v3/account` (`omitZeroBalances=true`) | балансы free/locked, права ключа (`canTrade`) |
| `commission(symbol)` | `GET /api/v3/account/commission` | реальные ставки maker/taker и скидка BNB |
| `open_orders()` | `GET /api/v3/openOrders` | сверка |
| `my_trades(symbol, from_id)` | `GET /api/v3/myTrades` | восстановление журнала (способ L метрики) |
| `book(symbol)`, `tickers()` | `depth`, `bookTicker`, `24hr` | цены для капитала и универсума |
| `test_order(...)` | `POST /api/v3/order/test` (`computeCommissionRates=true`) | проверка фильтров и комиссии без исполнения |
| `place_order(...)`, `place_oco(...)` | — | **есть в интерфейсе, но выбрасывают исключение**, пока `TRADING_ENABLED` и `TRADING_MODE == "demo"` не включены (этап C) |

**Поток пользователя** (исполнения, балансы): WS API `wss://demo-ws-api.binance.com/ws-api/v3`,
метод `userDataStream.subscribe.signature`. Он работает с HMAC-ключом без listenKey; механизм
listenKey Binance объявил устаревшим. Если на демо метод недоступен — запасной путь: опрос
`openOrders` + `myTrades` раз в 60 с. Доступность метода проверяется на гейте A.

**Фильтры биржи** — только из `exchangeInfo`, никаких констант в коде: `PRICE_FILTER` (tickSize),
`LOT_SIZE` / `MARKET_LOT_SIZE` (stepSize, min/max), `NOTIONAL` (min/max, применяется ли к
рыночным), `PERCENT_PRICE_BY_SIDE`, `MAX_NUM_ORDERS`, `MAX_NUM_ALGO_ORDERS` (лимит стоп-ордеров),
`TRAILING_DELTA`. Хелперы `round_qty`, `round_price`, `check_order(symbol, side, type, qty,
price)` возвращают список нарушенных фильтров. Отказ биржи (−1013, −2010) логируется с именем
фильтра.

**Лимиты запросов:** читаются из `rateLimits`, вес контролируется по заголовкам,
`TRADING_WEIGHT_BUDGET_SHARE = 0.5` (рекордер и бот делят лимит IP). 429 → `Retry-After`,
418 → полная остановка клиента и алерт в Telegram.

**Идемпотентность (заготовка для этапа C):** `newClientOrderId =
f"cb_{policy_epoch}_{sym}_{bar_ts}_{leg}"`. Повтор запроса после таймаута не создаёт второй
ордер: сначала `GET /api/v3/order?origClientOrderId=...`.

### `trader/trading_universe.py`

Раз в сутки (после `exchangeInfo`) → `trader/runtime/trading/universe.json` с версией и причиной
исключения по каждой паре:

1. На демо: `status == "TRADING"`, `quoteAsset == "USDT"`, `isSpotTradingAllowed`, `ocoAllowed`, в
   `orderTypes` есть `MARKET`, `LIMIT`, `STOP_LOSS_LIMIT`.
2. Исключить: стейблкоины и фиат против USDT (`USDC`, `FDUSD`, `TUSD`, `EUR` …), токены с плечом
   (`*UP`, `*DOWN`, `*BULL`, `*BEAR`).
3. **Ликвидность** по данным A0 за 7 дней:
   - `TRADING_UNIVERSE_MIN_QUOTE_VOL_USDT` — 24ч оборот на живом рынке (медиана);
   - `TRADING_UNIVERSE_MAX_SPREAD_BPS` — медианный спред на демо;
   - `TRADING_UNIVERSE_MAX_IMPACT_BPS` — стоимость рыночной покупки на размер позиции, p95;
   - `TRADING_UNIVERSE_MAX_DIVERGENCE_BPS` — |mid демо − mid живого рынка|, p95.

   Пороги **выставляются по распределениям A0 на гейте A** и записываются в эту спеку с цифрами.
   До этого фильтр не применяется.
4. Пара без истории 15m/1h (меньше 2 000 баров) получает статус `needs_history` и до бэкфилла
   (этап B) не торгуется.

## Исправление 2026-10-10: зависание рекордера под планировщиком

**Что произошло.**
- Снимок, запущенный по расписанию, висел больше 10 минут.
- Планировщик через 4 минуты завершал `cmd`, но дочерний Python оставался жить и держал журнал
  открытым. Следующие запуски не могли в него писать.
- Сторож (`faulthandler`, 200 с) показал место зависания: чтение тела ответа
  `GET /api/v3/exchangeInfo`. Это ответ на мегабайты по всем 3 724 парам, и рекордер просил его в
  каждом снимке.
- Тайм-аут сокета (10 с) срабатывает только при полном молчании соединения. Медленный поток
  данных он не ловит.

**Требования (проверяются тестами до кода):**
1. **Общий срок на запрос.** `ExchangeClient._request` прерывает запрос, если от отправки до
   конца чтения тела прошло больше `REQUEST_DEADLINE_SEC = 30` секунд, даже если данные идут.
   Ошибка `RequestDeadline` без повтора внутри клиента.
2. **`exchangeInfo` не чаще раза в сутки.** Ответ кэшируется на диске:
   `trader/runtime/trading/exchange_info.json`, с временем получения. Рекордер и универсум
   берут кэш, если ему меньше `EXCHANGE_INFO_MAX_AGE_SEC = 86400`. Если кэша нет или он
   испорчен — запрос, иначе сеть не трогается.
3. **Сторожа процессов:** снимок рекордера ≤ 200 с, снимок капитала ≤ 60 с (`faulthandler`
   печатает стек и завершает процесс). Лимит задачи планировщика 5 минут больше их суммы.
4. **Порядок в `run_recorder.cmd`:** сначала капитал (короткий), потом микроструктура.

5. **Приоритет задачи — обычный.** Причина вторая (18:00): по умолчанию задача планировщика
   получает приоритет 7 (`BelowNormal`). При загрузке процессора 100% (другие Python-процессы
   на машине с приоритетом Normal) процесс снимка за 8 минут получил 0.23 с процессора, и даже
   `GET /api/v3/time` шёл дольше 30 с. `curl` в тот же момент отвечал за 1–2 с. Задача
   `CryptoBot_MicrostructureRecorder` должна иметь приоритет ≤ 6 (Normal); проверка —
   `trader/test_recorder_hang_fix.TestSchedulerTask`.

**Сделано в порядке спека → тесты → код** (правило оператора 2026-10-10):
- `trader/test_recorder_hang_fix.py` написан до кода. 7 из 10 тестов упали на старом коде.
  Сторожа и порядок в `cmd` уже были сделаны раньше правила, поэтому эти 3 теста прошли сразу.
- Код: `ExchangeClient._request` читает тело кусками и прерывается по `REQUEST_DEADLINE_SEC`;
  `microstructure_recorder.cached_exchange_info()`; универсум берёт тот же кэш.
- Подтверждение причины: кэш `exchange_info.json` весит **19 МБ**. Рекордер скачивал его
  каждые 5 минут.

## Исправление 2026-10-12: сетевые ошибки обрывали снимок

**Что было.** За 11–12.10 три снимка из ~540 потеряны: в 14:56, 04:01 и 11:36. Причина —
`TimeoutError` (тайм-аут чтения или SSL-рукопожатия) вылетал из `ExchangeClient._request` мимо
`ExchangeError`, а рекордер ловит только `ExchangeError`.

**Требование:**
- любая сетевая ошибка (`URLError`, `TimeoutError`, `OSError`) превращается в
  `ExchangeError(status=None, code="network")`;
- `RequestDeadline` остаётся отдельной ошибкой.
